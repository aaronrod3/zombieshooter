## Naming (critical)
- `ZS` prefix for all non-zombie classes/assets: `AZSPlayerCharacter`, `AZSGameMode`, `AZSGameState`, `AZSPlayerState`, `AZSPlayerController`, `AZSWeapon`, `UZSHealthComponent`, `UZSWeaponConfig`, `BP_ZS_*`, `DA_ZS_*`, `WBP_ZS_*`.
- "Zombie" reserved only for enemy: `AZombieCharacter`, `AZombieAIController`, `BP_Zombie_*`. Never mix — player must never be confused with enemy.
- Input Actions unprefixed (`IA_Fire`); Input Mapping Contexts prefixed (`IMC_ZS_Default`).

## Commands
- Build (Editor): Rider/VS → `ZombieShooterEditor Win64 Development`, or `Build.bat ZombieShooterEditor Win64 Development -project=...uproject -waitmutex`
- Gen project files: `Build.bat -projectfiles -project=...uproject -game -engine`
- Test: PIE for gameplay feel/visuals/multiplayer (Multiplayer Options, Players ≥2, listen-server) — still needs a human, no way around it (no PIE-input automation path exists, see MCP/Editor Tooling below). For pure server-logic/state/math, `Source/ZombieShooter/Tests/` holds headless Unreal Automation Tests. **Always pass an explicit `-log=`** — the default log path silently fails to run at all while the GUI editor is open. Components spawned for a test need to be real constructor subobjects (`ZSTestHarnessActor.h`), not post-spawn `NewObject`+`RegisterComponent()` — the latter doesn't reliably get `BeginPlay()` called in a synthetic test world. Live Coding does **not** reliably pick up changes under `Tests/` — full `Build.bat` rebuild only. **Building/running this suite, and any editor close/rebuild it requires, is present-session/dev-triggered only — never during an away session.** Exact commands/protocol: `Docs/CommandReference.md` (graceful close only, never force-kill; no save-first or remote-command-injection path exists). Away-session rule: `Docs/AsyncSessionProtocol.md`.
- Header change → regen project files if needed. Live Coding (Ctrl+Alt+F11) OK for .cpp-only.
- Git + LFS, branch `main`. Commit after each sub-task. Never force-push main.

## Architecture
- **Framework/**: `AZSGameMode` (server rules), `AZSGameState` (replicated world clock — `TimeOfDayHours`/`DayCount`/utilities-shutoff timer — plus sleep/time-skip readiness aggregation across `PlayerArray`, and the finite per-session rarity loot pool used by `Inventory/`), `AZSPlayerState` (health/ammo/kills, unpopulated), `AZSPlayerController` (Enhanced Input via `IMC_ZS_Default`+`IMC_ZS_MouseLook`, wired via `ConstructorHelpers::FObjectFinder`, not BP CDO).
- **Player/**: `AZSPlayerCharacter` — TopDown is the **only** camera now (fixed pitch/yaw; `EZSCameraPerspective`/`ToggleCameraPerspective`/the ThirdPerson path were deleted B0-T3.9, dev-confirmed permanent, no fallback). `Player/ZSCameraDirector` (an `ActorComponent`, not self-ticking — the character's own `Tick()` drives it) owns zoom: a push/pop `EZSCameraContext` stack (`Outdoor`/`Interior`/`Underground`/`Driving`-reserved) for auto-zoom presets, plus a manual-override layer (`ApplyManualZoom`) that fully disengages auto-zoom until a context change moves away from wherever the override started. `Framework/ZSElevationSubsystem` (a `UWorldSubsystem`) answers "what Z-plane is this actor on" for `GetCursorGroundLocation`'s ground-plane projection — B0 ships a single-floor stub, B4 swaps the body for real multi-level. Hybrid cursor facing (`UpdateCursorFacing`) overrides actor rotation toward the mouse cursor's ground-plane projection, gated to aiming/attacking/interacting only. Move/look/jump/crouch/sprint/aim/fire/reload/melee are all server-RPC+OnRep replicated. Weapon equip is config-driven through 4 fixed weapon-mount slots (`UZSInventoryComponent::MountedLongGuns[2]`/`MountedSidearm`/`MountedMelee` — the last added 2026-08-06), each key-bound directly (`1`/`2`/`3`/`4` → Primary/Pistol/Secondary/Melee) plus a 5th Equipment slot (`G`, any carried `UZSWeaponConfig`) — replaces the original free-form 9-slot `HotbarSlots` array design (B1, 2026-08-01, superseding OQ-B0-01's "hotbar is 1-9 direct-select" resolution; scroll wheel is still camera zoom, not hotbar cycling). A weapon becomes key-selectable purely by being mounted, no separate assignment step. `CurrentWeapon` **is** the active slot (deliberately not renamed to avoid a Blueprint-reference-corruption risk, see the Live Coding lesson below). `SelectHotbarSlot`/`ResolveWeaponSlotInstance` resolve a 0-based weapon-key index live from whichever mount/Equipment reference it maps to; `Server_SelectHotbarSlot` schedules the actual equip after `EquipTimeSeconds`/`UnequipTimeSeconds`, gated by `bIsBusy`. Mount eligibility partitions cleanly by `Handedness`/`AttackType`: `MountedLongGuns` gates on `Handedness==TwoHanded` alone (a two-handed melee weapon, e.g. an axe, mounts here too — "long gun" is a naming holdover, not a real restriction); `MountedSidearm` gates on `OneHanded`+`Ranged`; `MountedMelee` gates on `OneHanded`+`Melee`, the exact converse of the sidearm gate (closes the gap where a one-handed melee weapon, e.g. a knife, previously had no dedicated mount at all). `IA_Attack` dispatches on `CurrentWeapon->GetConfig()->AttackType` (`EZSAttackType`, `ZSWeaponTypes.h`) — `Ranged` into a spread-cone hitscan/projectile fire (`Server_Fire`, cone via `FMath::VRandCone`, headshot weighting via a `Hit.BoneName` override — B0-T3.5/T3.6), `Melee`/no-weapon into `PerformMeleeSwing` (shared bare-fist/weapon-melee logic, now costs Stamina per swing and excludes downed zombie targets — B0-T10.3/T10.5). `SecondaryHand` (B0-T11): a GUID slot alongside `HotbarSlots`, holding either a one-handed+`bUsableInSecondaryHand` weapon or any `bIsToggleable` item (a flashlight — `FlashlightComponent`, a real `USpotLightComponent`); `IA_SecondaryAction` dispatches on the resolved config's type — toggle for items, full fire/melee for weapons (B0-T11.2, mirrors `CurrentWeapon`'s lifecycle; detail in `B0_Stabilization.md`). `Player/Animation/UZSAnimInstanceBase` = native TP AnimBP parent. **Not yet built**: Shove, Mount/Climb (both bundled on the same `Space` input as the T10.6 finisher, genuinely undesigned).
- **Interaction/**: `UZSInteractableComponent` — attach to any actor to make it interactable; `AZSPlayerCharacter::TryInteract`/`Server_Interact` is the server-authoritative entry point, `UpdateNearestInteractable` does a per-tick sphere-overlap scan against `ECC_WorldStatic`/`ECC_WorldDynamic`. No world-prompt widget yet — `OnNearestInteractableChanged` is the C++ hook for one.
- **Survival/**: `UZSNeedsComponent` — replicated Hunger/Thirst/Fatigue/Stamina/Wet/Temperature, rates/curves from `UZSNeedsConfig`. Hunger/Thirst/Fatigue/Temperature decay/tick on `AZSGameState`'s game-hour clock; Stamina is real-time (drains sprinting — scaled by inverse encumbrance, B0-T4.8 — regens idle), gates `StartSprint`. `Wet` (B0-T4.1, debug-only `Server_SetWet` until B4's weather exists) auto-dries after `WetDryOutGameHours` and feeds both `Temperature`'s target (B0-T4.3, four inputs: neutral/wet/indoor/clothing-insulation-sum) and periodic movement noise (`AZSPlayerCharacter::TickWetFootstepNoise`, B0-T4.2 — dry footsteps report nothing). `GetPerformanceMultiplier()` (Hunger/Thirst/Fatigue/Temperature, performance-only, provably never exceeds 1.0) feeds healing rate/aim accuracy/attack recovery; `GetPerceptionMultiplier()` (Fatigue-driven, B0-T4.6) is a separate presentation-only stub for a future vignette/audio pass, never touches gameplay math. Four `GetXSeverityTier()` accessors (Hunger/Thirst/Fatigue/Stamina/Temperature) share one 4-tier scale off `UZSNeedsConfig`. `UZSItemConfig` is the eat/drink/use data contract, consumed via `Server_ConsumeItem`/`Server_UseItem`; also carries `bIsToggleable` (B0-T11, an activatable item like a flashlight) and `InsulationValue` (clothing → Temperature). Sleep/time-skip: `AZSPlayerCharacter::RequestSleep`/`CancelSleepReady` (per-player ready flag) + `AZSGameState::UpdateSleepRequestState` (all-players-ready aggregation + clock advance); `IsSafeToSleep()` is real for the aggro-cooldown half (`Server_NotifyHostileDetection`, called from zombie perception) but the "real shelter" half is still stubbed `true` (B0-T4.10 — no indoor/barricade system exists, B4's job). No moodle UI yet — `OnHungerChanged`/etc. are the hooks.
- **Weapons/**: `AZSWeapon` (replicated config/fire-mode/ammo; root component `BaseWeaponMesh`, a `UStaticMeshComponent` — no skeletal weapon meshes anywhere), `UZSWeaponConfig` (the full per-weapon data contract: Setup meshes (`BaseWeaponMesh`/`TriggerMesh`/`MagazineMesh`/`TP_Mesh`), Attachments (`MuzzleMesh`/`HandguardMesh`/`GripMesh`/`OpticMesh`, each with its own `SocketX` field), fire/melee/durability/knockback tunables, `AttackType`, aim-cone spread + headshot-weighting fields (`HipFireSpreadDegrees`/`AimedSpreadDegrees`/`HipFireHeadshotChance`/`AimedHeadshotChance`, B0-T3.5/T3.6), jamming fields (`bJamImmune`/`BaseJamChance`/`MaxJamChance`/`TP_ClearJam`, B0-T10.1), `MeleeStaminaCost`/`FinisherMontage` (B0-T10.3/T10.6), and `Handedness`/`bUsableInSecondaryHand` (B0-T2.12) for `SecondaryHand` eligibility), `AZSProjectile` (opt-in per-weapon simulated projectile — `ProjectileClass` unset keeps the old instant hitscan path — replicated movement, damage/knockback/headshot-weighting on first blocking hit), `AZSMagazine` (cosmetic prop, also static-mesh-based), notify classes `AN_ZS_UnlockActions`/`ANS_ZS_BlockADS`/`ANS_ZS_LeftHandGrip`. `AZSWeapon::CurrentConditionQuality` (seeded from the carried `FZSItemInstance`, independent of the melee-only durability system) drives the jam-chance roll (`Server_RollForJam`, called from `Server_Fire` before ammo is consumed) and its own `bIsJammed`/`OnJamStateChanged`; cleared via `Server_ClearJam` (the "Rack Firearm" action). **Magazines, 2026-08-11**: reload is a real per-instance magazine swap now, not a flat reserve-ammo-pool pull — `UZSMagazineConfig` (a new `UZSItemConfig` subclass, `MagazineCapacity`/`CompatibleAmmoConfig`) is a carried, stateful item (`FZSItemInstanceState::CurrentAmmoCount`, lazy-resolves like durability); `UZSWeaponConfig::AmmoItemConfig` is now purely the compatibility key a magazine's own `CompatibleAmmoConfig` must match, no longer consumed directly. `AZSWeapon::CurrentMagazineInstanceId`/`CurrentMagazineConfig` track which specific carried instance is loaded (`Server_LoadMagazine`/`Server_EjectCurrentMagazine`/`FindBestCompatibleMagazine`); `AZSPlayerCharacter::PerformMagazineReload(bool bQuickReload)` orchestrates the swap — quick reload (`Q`, `QuickReloadTimeSeconds`) discards whatever's left in the ejected magazine, normal/tactical reload (`R`, `NormalReloadTimeSeconds`) stows it back into inventory with its remaining round count via `Server_AddItemInstance`. A loaded magazine is removed from `CarrySlots` entirely while in the gun (consumed, not equipped-and-referenced like gear/mounts) — same semantics the old reserve-ammo pull already had. Content gap: no `DA_ZS_MagazineConfig_*`/`IA_QuickReload` authored yet.
- **Combat/**: `UZSHealthComponent` — replicated `CurrentHealth` + 4 `FZSBodyZoneWound` (Head/Torso/Arms/Legs), each with a wound type (Scratch/Laceration/Fracture/Bite), bleed/dirty/splinted/amputated flags, a critical-head-bleed flag (`bCriticalBleed`, B0-T5.3, rare roll on a fresh Head bleed, steep override rate until bandaged), multi-day fracture recovery (`FractureRecoveryProgressGameHours` vs. `UZSHealthConfig::FractureRecoveryDurationGameHours`/`SplintedFractureRecoveryDurationGameHours`, B0-T5.4), and a **second, distinct** wound-infection state (`EZSWoundInfectionState`, B0-T6.1 — ordinary dirty-wound infection, escalates past `WoundInfectionOnsetGameHours` if untreated, cured instantly by disinfect/clean-bandage, worsens bleed/slows fracture recovery, never touches `CurrentHealth`) kept separate from bite infection (`EZSInfectionStage`) below. All damage flows through `AZSPlayerCharacter::TakeDamage` (zone inferred from hit bone name — headshot weighting can override this to Head, see Weapons/ above — wound type from the damage type class via `ZSDamageTypes.h`'s marker classes) into `Server_ApplyDamage` — nothing else mutates health directly, per the replication convention below. Bite wounds roll a hidden infection chance; `EZSInfectionStage` progresses on `AZSGameState`'s game-hour clock over a per-infection randomized 2-4 in-game-day total (`Min`/`MaxBiteInfectionDurationGameHours`, B0-T6.4), delayable per-treatment via `Server_DelayInfection`/`UZSItemConfig::MedicalIncubationDelayGameHours` (B0-T6.5) — **plainly, legibly shown in a future UI**, not deliberately ambiguous (B0-T6.3 reversed the original premise). `Server_AmputateZone` clears an active bite infection at the cost of a permanent zone penalty (any zone, solo-capable, no tool-item gate); now a real timed/`bIsBusy`-gated action (B0-T7.1) that ends in a temporary amputation-shock mobility penalty (`AZSPlayerCharacter::bIsAmputationShocked`/`AmputationShockDurationSeconds`/`AmputationShockMobilityMultiplier`, stacks on top of — doesn't replace — the permanent zone penalty above; player stays fully in control throughout, just slowly). Arm amputation blocks equipping a `TwoHanded` weapon (B0-T7.5). **2026-08-10, dev-confirmed — blackout removed entirely, replaced by 0-HP downed/revive**: amputation no longer incapacitates at all (the shock penalty above is its only consequence now); separately, hitting 0 HP (`Server_ApplyDamage`/`TickBleed`) routes through `HandleHealthDepleted()`, which unconditionally enters `UZSHealthComponent::bIsDowned` (a real `DownedDurationSeconds` — 2 min default — countdown to `Die()`, `Server_EnterDowned`) — solo included ("player can still be downed if no other players in the lobby, but just a lower chance at surviving a horde," dev-confirmed same session), since a solo player still gets the fight/self-heal/wait-it-out window, just with nobody able to `Server_ReviveDowned` them. While downed, the 4 DoT tick systems (bleed/infection/fracture-recovery/wound-infection) all pause, the player stays damageable (a fresh hit while already downed is a finishing blow — instant `Die()`) **and can still fight back** — `CanFire()`/`CanAttack()`/`CanSwitchLoadout()` no longer block on downed at all, just penalized: `GetAccuracySpreadMultiplier()` folds in `DownedAccuracySpreadMultiplier` (2.5× wider spread by default, stacks with the Arms-wound penalty), and `AZSPlayerCharacter::DownedActionSpeedMultiplier` (0.5× by default) slows every busy-action montage (`BeginBusyAction` — reload, jam-clear, etc.) and the hotbar weapon-swap timer (`Server_SelectHotbarSlot_Implementation`'s `SwitchDelay`) uniformly. Getting back up (self-heal or teammate revive alike) starts a further temporary movement-only penalty, `bIsPostReviveSlowed`/`PostReviveSlowDurationSeconds`/`PostReviveSlowMovementMultiplier` (10s at 0.5× by default), independent of and stacking with the amputation-shock multiplier. Self-revive via any `HealthRestore` item crossing `CurrentHealth` back above 0 (`Server_RestoreHealth` auto-exits downed) or teammate revive via `ReviveInteractable` (`Server_ReviveDowned`, floors `CurrentHealth` at `ReviveHealthAmount`) — the same interactable the old blackout system used, now gated on `IsDowned()` instead. Bite-infection's own `Critical`-stage death (`TickInfection`) is unaffected — still an instant, non-revivable `Die()`, a deliberately separate death vector from combat/bleed-out. `GetMobilityMultiplier()`/`GetAttackSpeedMultiplier()`/`GetReloadSpeedMultiplier()`/`GetAccuracySpreadMultiplier()` feed move speed, fire-rate timing, and (B1, 2026-08-02) weapon spread — the last one is the odd one out of the four, 1 = no penalty and *higher* is worse since it multiplies a spread angle rather than dividing a speed/rate; `AZSPlayerCharacter::FireWeapon` multiplies it straight into `SpreadDegrees` before the `VRandCone` roll. `GetWoundDisplayCondition(const FZSBodyZoneWound&)` (B1, 2026-08-02) is the single source of truth for "does this wound currently matter" — a 6-value `EZSWoundDisplayCondition` (None/Wounded/Bleeding/Fracture/Infected/Amputated, worst-wins priority), zone-aware since only Arms/Legs feed a multiplier at all; `HasAnyGameplayAffectingCondition()` aggregates all 4 zones + bite-infection into one bool. Death → `HandleDeath` → `Server_HandleDeathLootAndZombie` (drops every carried instance at the death location via `UZSInventoryComponent::Server_DropAllItems`, then spawns `AZSPlayerCharacter::DeathZombieClass` there — B0-T9.1/T9.2, unset class = content gap) → delayed `Destroy()` + `RestartPlayer` respawn (always the same persistent world, solo included, B0-T9.4). Treatment (`Server_ApplyBandage`/`Server_Disinfect`/`Server_Splint`) and item consumption both route through `Server_UseItem`, dispatching on `UZSItemConfig::EZSItemUseType`.
- **Zombies/**: `AZombieCharacter` — deliberately does not reuse `UZSHealthComponent` (that machinery is player-specific); just a flat replicated `CurrentHealth` seeded from `UZSZombieConfig::MaxHealth`, same `TakeDamage`-only-entry-point rule. A landed hit whose knockback strength meets `AZSPlayerCharacter::DownedKnockbackThreshold` (checked centrally in `ApplyHitKnockback`, so hitscan/projectile/weapon-melee/bare-fist all trigger it identically) enters a temporary **downed state** (`bIsDowned`, `Server_EnterDownedState`/`Server_ExitDownedState`, B0-T10.4) — auto-recovers after `UZSZombieConfig::DownedRecoverySeconds` unless finished first via the player's Space finisher (`AZSPlayerCharacter::Server_PerformFinisher`, B0-T10.6, branches bare-handed-stomp vs. equipped-weapon-downward-strike); a standing melee swing (`PerformMeleeSwing`) unconditionally excludes downed targets (B0-T10.5). `AZombieAIController` wires `AIPerception` (sight+hearing, radii from `UZSZombieConfig` at `OnPossess`) and runs `BT_Zombie`/`BB_Zombie` (`/Game/ZS/Enemy/AI/`) — `HandleTargetPerceptionUpdated` writes Blackboard keys, calls `SetChasing`, and notifies the sensed player's aggro-cooldown (`Server_NotifyHostileDetection`, feeds `IsSafeToSleep()`). `SetDowned` (called from the downed-state transitions above) sets the new `bIsDowned` Blackboard key and, until `BT_Zombie`'s graph is actually wired to branch on it (content gap, no editor/MCP access when this was built), pauses/resumes the whole tree directly via `BrainComponent` as a functional stand-in. `Zombies/AI/` holds all 6 BT task nodes as native C++ (`BTTask_MeleeAttack`/`StartInvestigationTimer`/`StartIdleDwell`/`Wander`/`GetInvestigationPoint`/`ClearLastKnownLocation`, sharing key names via `ZSZombieBlackboardKeys.h`) — no content-Blueprint BT task wrappers. Verified working in PIE (wander/investigate/chase). `UZSZombieConfig` covers speed/health/senses/damage/mesh/anim-class/BT/`DownedRecoverySeconds` per zombie type — a second type is a new config instance, never a C++ branch, per the multi-config rule below. `UZSNoiseSystem::ReportNoise` (wraps `UAISense_Hearing::ReportNoiseEvent`) is wired into weapon fire (`FireNoiseRadius`), sprint start, and periodic wet-footstep movement noise (`AZSPlayerCharacter::TickWetFootstepNoise`). `ZS.SpawnZombies <n>` (host-only console command, `AZSGameMode::StressTestZombieClass`) spawns a scattered batch for profiling (B0-T12.1) — works in any level; the dedicated `Lvl_ZS_StressTest` graybox map itself isn't built (content gap).
- **Inventory/**: `Inventory/ZSItemInstance.h` — `FZSItemInstance` (stable `FGuid InstanceId` + `Config` + `StackCount` + `Location` (`EZSCarryLocation`) + `FZSItemInstanceState` (`CurrentDurability`/`ConditionQuality`, meaningful only when `StackCount == 1`)) is, per B0-T2 Step A (2026-07-26), the one way an item exists anywhere in `Inventory/` — replaces the old bare `Config`+`Count` pairing everywhere except the hotbar/equip slots (see Known gap below). Stackable and per-instance-stateful are mutually exclusive by construction; a merge into an existing stack always discards whichever instance's identity doesn't survive it. `UZSWeaponConfig` now inherits `UZSItemConfig` (B0-T2 Step B) so a carried weapon can exist as a real `FZSItemInstance` at all. `UZSInventoryComponent` — replicated flat `CarrySlots` (`TArray<FZSItemInstance>`) + `EquippedSlots` (2026-08-06: a fixed-size `TArray<FGuid>` indexed by `EZSEquipSlot`, `NumEquipSlots = 12` — mirrors `MountedLongGuns`' own "always sized, index is the identity" pattern; was two bare `FGuid`s, `Back`/`Hip` then `Back`/`Duffle`, before the real 11-value clothing+gear system landed). `EZSEquipSlot` (`Survival/ZSItemConfig.h`) is two families laid out on opposite sides of the Loadout tab's character model — Clothing (`Head`/`Eyes`/`Mask`/`Shirt`/`Pants`/`Shoes`) and Gear (`Helmet`/`Vest`/`Belt`/`Backpack`/`Duffle`) — with `Vest`/`Belt`/`Backpack`/`Duffle` container-bearing (their own fixed-grid `GetCompartmentCapacity` compartment: Pockets 4/Vest 8/Belt 8/Backpack 20/Duffle 18 slots — Backpack shrunk from 24 (4x6) to 20 (4x5) 2026-08-07 to fit the Loadout/ContainerLoot compartment-stack's vertical budget), `Pants` gating the pre-existing `EZSCarryLocation::OnPerson` (Pockets) compartment instead of owning one itself, and equipping `Helmet` force-unequipping `Head` (one-way only). Container-bearing items grant `CarryCapacityBonus` while worn. `GetSlotsInLocation` resolves `OnPerson` from flat `CarrySlots` (excluding anything equipped/weapon-mounted) but resolves `Vest`/`Belt`/`Backpack`/`Duffle` through the equipped bag's own `ContainedItems` instead — `Server_StoreInBag`/`Server_RetrieveFromBag`/new `Server_RetrieveFromAnyEquippedBag` are what move an item between the two. `Server_AddItem`/`Server_AddItemInstance` atomically reject a pickup that would overflow Pockets' capacity (item stays in the world/container, not silently destroyed) rather than defaulting to a hard carry block. `AZSPlayerCharacter::WornMeshComponents` (11 `UStaticMeshComponent`s) + `RefreshWornMeshes()` attach each equipped item's `UZSItemConfig::WornMesh` (static mesh) to `GetSocketForEquipSlot`'s socket, bound to `OnInventoryChanged`; a `USceneCaptureComponent2D` + per-instance `IsLocallyControlled()`-gated `UTextureRenderTarget2D` (`GetPreviewRenderTarget()`) capture just those meshes for the Loadout tab's live 3D preview (`UZSCharacterPreviewWidget`), recaptured at the end of every `RefreshWornMeshes()` call. `Server_AddItem(Config, Count)` mints fresh instance(s) (new GUID per non-stackable unit); `Server_AddItemInstance(FZSItemInstance)` adds an already-existing instance, preserving its GUID/state if non-stackable or merging its `StackCount` in if not — this is what a dropped weapon's durability survives on re-pickup. `Server_RemoveItem`/`Server_RemoveInstanceById` return the actual instance(s) removed (whole instance if fully consumed, a freshly-GUID'd fragment if only a stack was partially consumed) rather than a bare count, so `Server_DropItem`/`Server_DropAllItems` can hand each one to its own `AZSWorldItemActor`. **Equipping (hotbar and gear slots alike) never physically removes an instance from `CarrySlots`** — a slot just holds a `FGuid` reference into an instance that stays resident there, which is what makes a bag's own contents (`FZSItemInstance::ContainedItems`, `Server_StoreInBag`/`Server_RetrieveFromBag`, B0-T2.9) survive equip/unequip/drop for free, and what `Server_DropAllItems` (B0-T9.1, called on player death) relies on to sweep hotbarred/equipped items too without special-casing them. Loot rolls a `ConditionQuality` (0-1) per instance, banded by rarity tier via `AZSGameState::RollConditionQuality` (B0-T2.10). `GetEncumbranceMultiplier()` folds into move speed alongside `Combat/`'s mobility multiplier — a soft penalty past capacity, not a hard carry block. `AZSWorldItemActor` is a replicated pickup (reuses `Interaction/`'s `UZSInteractableComponent`) holding one `ItemInstance` (`VisibleAnywhere`, code-set only) — `InitializeItem(Config, Count)` mints a fresh instance (the hand-placed/pre-populated-pickup path, e.g. a Blueprint subclass calling it in `BeginPlay`), `InitializeFromInstance(FZSItemInstance)` preserves an existing one (the drop path, called from `Server_DropItem`/`Server_DropAllItems`). `AZSContainerActor` (same interactable reuse) seeds `ContainerSlots` (`TArray<FZSItemInstance>`, `Location = World`) from a `UZSLootTableConfig` at `BeginPlay` and does a "loot all" transfer (`Server_AddItemInstance` per slot) on interact; its `LootTable` field is `EditDefaultsOnly`, so per-archetype containers need a Blueprint subclass (e.g. `BP_ZS_Container_Kitchen`), not a raw placed `AZSContainerActor`. Rare/VeryRare rolls are gated through a finite per-session pool on `AZSGameState`. Reserve ammo is a real, lootable, stackable `UZSItemConfig` too (`UZSWeaponConfig::AmmoItemConfig` names which one a weapon reloads from, B0-T2.11) — no more flat `CurrentReserveAmmo` counter.
- **UI/**: `UZSUIManager` (a `ULocalPlayerSubsystem`, B1-T1) owns the modal input-mode stack — `PushModal`/`PopModal(FName ModalTag)`, `IsAnyModalActive()` — that every B1 screen pushes onto. Pushing the first modal adds `IMC_ZS_UI` to the local player's Enhanced Input subsystem at a higher priority than `IMC_ZS_Default` (added at priority 0 in `AZSPlayerController::SetupInputComponent`); popping the last removes it. `AZSPlayerCharacter::GetUIManager()` is the one lookup point gameplay code uses to ask "is a menu open" — `HandleAttack()` and `IsCursorFacingActive()` both hard-guard on it directly (not relying solely on Enhanced Input's cross-context consumption) so a menu-open click can't leak through as an attack or fight the cursor-facing turn. `UZSUserWidgetBase` (B1-T2.1/T2.4, the one shared parent every `WBP_ZS_*` inherits) carries convenience getters (`GetOwningZSPlayerCharacter`/`GetOwningHealthComponent`/`GetOwningNeedsComponent`/`GetOwningInventoryComponent`/`GetOwningZSGameState`/`GetOwningZSGameInstance`/`GetUIManager`/`GetNotificationSubsystem`) plus protected `PushAsModal`/`PopAsModal` wrappers. **2026-08-02 architectural shift**: every B1 widget (HUD, inventory/loot, death/blackout/sleep, main menu/pause/loading — `WBP_ZS_Settings` is the one holdout) is now built as a dedicated `UZSUserWidgetBase` subclass in `Source/ZombieShooter/UI/` rather than a Blueprint-only Graph tab — `BindWidget`/`BindWidgetAnimOptional` auto-bind Designer-tab widgets/animations by exact name, and `NativeConstruct()` does all delegate binding/refresh natively; the Blueprint side is hierarchy layout + Class Defaults only. Full class list and per-screen build steps live in the UI Build Manifest (linked from `Docs/Beta/B1_UI_UX.md`), not here. This pass also fixed a latent bug: `UZSInventoryComponent::Server_EquipToSlot`/`Server_MountLongGun`/`Server_MountSidearm` are plain `HasAuthority()`-gated calls, not real RPCs, so calling them from a client-owned widget silently no-ops on non-host clients — `AZSPlayerCharacter` now has matching `Server, Reliable` RPC wrappers that the equip/mount-slot widgets call instead. **Slot-widget convention (mandatory, confirmed 2026-08-09)**: an equip/mount/item slot widget never collapses itself when empty — an empty slot is still real, visible UI (a future background-image pass renders behind the icon). Only the icon content clears (`Image_Icon->SetBrushFromTexture(bIsEmpty ? nullptr : ...)`), visibility always stays `SelfHitTestInvisible`. `UZSItemSlotWidget::RefreshFromInstance` set this pattern first; `UZSWeaponMountSlotWidget`/`UZSEquipSlotWidget`/`UZSEquipmentSlotWidget`/`UZSSecondaryHandSlotWidget` originally collapsed instead and were fixed to match. The one thing that *is* allowed to collapse is a container/compartment panel itself (`UZSCompartmentPanelWidget`'s `GatingSlot`) when its bag isn't worn at all — a worn-but-empty bag still shows all its slots.
- **Replication convention (mandatory)**: `UPROPERTY(ReplicatedUsing=OnRep_X)` + `Server_X()` gated by `HasAuthority()` + `GetLifetimeReplicatedProps()`/`DOREPLIFETIME()` + `OnRep_X()` broadcasts a delegate. Never poll replicated state directly.
- **Multi-config rule**: every weapon or zombie system must generalize to N types via new config data-asset instances, never new C++ branches.
- **Cosmetic attachments must be `NoCollision`**: any mesh rigidly attached to the character (weapon meshes, future held items/clothing) needs collision explicitly disabled. Left at a default blocking profile, it overlaps the owning character's own capsule every tick and `CharacterMovementComponent`'s penetration-resolution logic fights that overlap indefinitely — visible as the character climbing or sliding uncontrollably the instant the mesh attaches. `AZSWeapon::AssignNewStaticMesh` already does this for attachment sub-meshes; anything built directly in a constructor (like `BaseWeaponMesh` itself) needs the same explicit `SetCollisionEnabled(ECollisionEnabled::NoCollision)` call.

## Conventions
- Epic naming standard (`AMyActor`, `UMyComponent`, `FMyStruct`, `EMyEnum`, `IMyInterface`) + ZS/Zombie rule.
- Booleans: `b` prefix. Pointers: `TObjectPtr<T>` in UPROPERTY, raw `T*` locally.
- `GENERATED_BODY()` on all reflected classes.
- Server mutators prefixed `Server_`. No magic numbers — tunables in `UZSWeaponConfig`/EditAnywhere. Damage only via `TakeDamage()`/`ApplyDamage`. No commented-out code — use branches. Check `Build.cs` before adding heavy modules.
- **Tech split**: C++ = base classes/data contracts/perf-sensitive/shared machinery. Blueprint = gameplay config/tuning. Player/weapon action functions are `BlueprintNativeEvent` so BP children can override without recompiling. AnimGraphs/data assets/BT stay Blueprint.

## Workflow Efficiency (lessons, keep this section short)
- **Don't auto-attempt `Build.bat` while the editor's likely open.** It fails on the Live Coding lock nearly every time (see below) — a wasted round-trip for zero information. State that a rebuild is needed and let the dev trigger it (Rider/Ctrl+Alt+F11), rather than spending a call finding out again.
- **Live Coding (Ctrl+Alt+F11) can silently corrupt Blueprint references to native classes, project-wide, on any patch — broader than just "the class that changed."** Two confirmed incidents, 2026-07-21, same session: (1) after a patch added new `UPROPERTY`s to `AZSPlayerCharacter`, `BP_ZS_PlayerCharacter`'s parent-class link broke (`BlueprintGeneratedClass BP_ZS_PlayerCharacter_C is not a child class of Class ZSPlayerCharacter`), so `AZSGameMode`'s `ConstructorHelpers::FClassFinder` silently fell back to the raw C++ class (wrong pawn, no BP CDO defaults, e.g. no mesh). (2) Separately, three unrelated Blueprints (`BTTask_MeleeAttack`/`StartInvestigationTimer`/`StartIdleDwell`) each had a `Cast To ZombieAIController` node break (`this cast has an invalid target type - was the class deleted without a redirect?`) even though `AZombieAIController`'s header hadn't changed that round at all - the corruption surfaced only once those Blueprints were first *loaded* post-patch (triggered here by an unrelated `unreal-mcp` property read), not at patch time itself. **The real rule: Live Coding reinstances every class in the module on every patch, so any Blueprint anywhere with a cast/reference to a native class in that module is at risk, whether or not that specific class was touched.** No crash, no visible editor error in either case - just silently wrong behavior. Diagnosed both via `EditorToolset.LogsToolset.GetLogEntries`/`BlueprintTools.compile_blueprint`, not guessing. **When a dev reports something that "should just work" behaving wrong after a Live Coding recompile, check the Output Log for `is not a child class of` or `invalid target type` before anything else** (or proactively run `BlueprintTools.compile_blueprint` on any Blueprint about to matter for a test). Reopening/recompiling a broken Blueprint parent-link self-heals; a broken Cast node needs the node itself deleted and recreated (compiling alone doesn't fix it - confirmed via `compile_blueprint` still failing with the stale node in place). Prefer a full editor Compile or `Build.bat` over Ctrl+Alt+F11 whenever practical, and after any Live Coding patch, consider a "Compile All Blueprints" pass (Content Browser bulk action) before trusting PIE results.
- **Check for a running editor with PowerShell's `Get-Process`, not Bash's `tasklist //FI`** — confirmed 2026-07-21 that a `tasklist` image-name filter run through the Bash tool silently matched nothing (wrong quoting through the POSIX-shell layer) while `UnrealEditor.exe` was, in fact, running; `Get-Process | Where-Object ProcessName -match "Unreal|LiveCoding"` caught it correctly. Also: **invoke `Build.bat` via the PowerShell tool, not Bash** — Bash's quoting mangles the batch file's internal `%~dp0`-style calls on this machine (`'C:\Program' is not recognized...`) even when the outer command looks correctly quoted; PowerShell runs it cleanly.
- **`Docs/SessionHandoff.md` is the sole owner of verification status** ("compiled?", "PIE-tested?", "what's next"). `CLAUDE.md`'s Architecture section describes what exists / current-state design — don't restate compile/test status in more than one place, or every status change becomes a multi-file edit.
- **Use targeted reads for large, mostly-static docs** (`GameDevPlan.md`, long class headers) — `Grep` with context or `Read` with offset/limit — instead of reading the whole file when only one section is relevant.
- **Keep TaskCreate/TaskUpdate granularity coarse** — one task per major deliverable/system, not per file. Fine-grained tasks multiply tool-call round-trips without adding real visibility for a solo-dev session.

## MCP / Editor Tooling (lessons, keep this section short)
- `.mcp.json` only proposes the `unreal-mcp` server; actual enablement lives in `.claude/settings.local.json` (gitignored) — won't exist on a new machine until recreated.
- `describe_toolset` on a large toolset (e.g. `BlueprintTools`) can return 70K+ characters — don't call it broadly. Prefer calling a tool blind with a guessed schema first; the error response echoes the exact required schema, which is cheaper than a full describe dump.
- Simulated PIE input (keypresses, viewport clicks) via MCP does **not** reliably reach the pawn — confirmed 2026-07-20 (a simulated `W` never moved `CharMoveComp.Velocity`). Separately, `computer-use` GUI automation can't even resolve the Unreal Editor window as a controllable app at all (`request_access` returns `notInstalled`, confirmed 2026-07-29) — there is no PIE-testing automation path right now, not just an unreliable one. Don't spend calls trying to force real gameplay-input verification headlessly; that needs the dev's hands, same as every past multiplayer/input check in this project.
- Poking a replicated/movement-authoritative property directly via `ObjectTools.set_properties` (e.g. `ACharacter::bIsCrouched`) can silently revert next tick if the owning component re-derives it every frame (e.g. from `bWantsToCrouch`) — a "successful" write isn't proof the state actually changed.
- **A live PIE Details panel can show a replicated `TArray`-of-struct component property (e.g. `UZSHealthComponent::BodyZones`) as empty/greyed even when the real data is present and correct** — confirmed 2026-07-29: dev saw `BodyZones` empty in Details mid-fight while health was visibly dropping, but `ZS.DebugListWounds`' log dump at the same moment showed the correct, fully-populated zone/wound data (Torso: `WoundType=Bite`, `Bleeding=1`, matching the bite-infection-roll log that had just fired). Root cause not confirmed (likely a Details-panel refresh quirk, not re-tested), but the lesson holds either way: **don't trust an apparently-empty replicated array in a live Details panel as proof of a bug** — cross-check via a debug console command/log dump first, the same way this one was resolved.
- **AnimGraph editing**: `read_graph_dsl`/`write_graph_dsl` return empty for AnimGraph-specific node types (`AnimGraphNode_*`) — use `find_nodes`/`get_node_infos`/`create_node`/`connect_pins` instead, which do support them. Normal EventGraphs (Blueprint logic, not AnimGraphs) work fine with `read_graph_dsl`/`write_graph_dsl`.
- **`FAnimNode_BlendListByBool`'s branch indexing is inverted from the naive bool-to-int mapping**: `bActiveValue == true` selects `BlendPose_0` (index 0), `false` selects `BlendPose_1` (index 1). `create_node`/`connect_pins` don't validate node *semantics*, only pin *connections* — when wiring a new `BlendListByBool`, verify the true/false assignment against a known-working sibling node's wiring, not against intuition.
- **`BlendSpacePlayer` X/Y pins don't self-document which locomotion variable belongs where — verify against the blend space asset's own `blendParameters` axis order, never assume by convention.** Root-caused 2026-08-11: the player was stuck in a frozen idle/rifle-idle pose while genuinely moving (not a T-pose — the AnimGraph was fully connected and compiling clean, so nothing *looked* broken from the graph-structure level). `ObjectTools.get_properties` on the blend space asset (`sampleData`/`blendParameters`) showed `BS_ZS_Unarmed_Idle_Walk_Run`'s real axis order is `[X=Direction(-180..180), Y=Speed(0..600)]`, but `find_nodes` with a variable-name `title` filter (e.g. `"groundSpeed"`) proved the AnimGraph had `groundSpeed → X` and `direction → Y` wired — backwards. Since straight-forward movement has `direction≈0`, that 0 was landing in the Y/Speed slot and permanently selecting the Idle sample regardless of actual speed. `BS_ZS_UnequippedCrouchWalk` had the same shape of bug one axis over: it's a direction-only in-place stepping cycle (`sampleData` show a Fwd/Back/Left/Right spread on X, Y always 0, no true idle sample) but its single X pin was wired to `groundSpeed` instead of `direction`. Fixed via `break_pins`/`connect_pins` (get exact `PinID`s from a prior `get_node_infos` call, since pins are addressed by `{direction, index_id, node}` not by name) + `compile_blueprint` + `AssetTools.save_assets`. **Diagnostic pattern for a future "wrong locomotion pose plays" bug**: don't just check the AnimGraph *compiles* and is *connected* — pull `blendParameters` off the actual blend space asset and cross-check its real axis semantics against which AnimInstance variable feeds each pin via `find_nodes(title=<var name>)`.
- **No `unreal-mcp` toolset can create Input Action or Input Mapping Context assets** (confirmed 2026-07-30, surveying `AssetTools`/`ObjectTools`/`BlueprintTools`/`DataAssetTools`) — `UInputAction` isn't a `UDataAsset` subclass so `DataAssetTools.create` won't take it, `BlueprintTools.create` only makes Blueprint classes, and there's no generic "instantiate an arbitrary UObject asset" tool. `ObjectTools.set_properties` could in theory hand-edit an existing IMC's `Mappings` array via JSON, but round-tripping `FEnhancedActionKeyMapping`'s instanced trigger/modifier structs through that path is untested and not worth the risk over the proven path. Every Enhanced Input asset in this project (see the many "not yet created as a .uasset - needs manual creation in-editor" notes throughout this file) is manually authored for exactly this reason - don't spend calls trying to force it through MCP.
- **`SkeletalMeshTools.add_socket`'s `bone_name` argument silently fails for at least some bones** (confirmed for a real, non-virtual bone on this project's skeleton — `weapon_r`, verified via the Skeleton Tree UI) — the new socket ends up parented to `root` instead, with only an oblique `SetSocketParent... bone named 'None'` log line as a clue, no thrown error. Works fine for other bones (e.g. `pelvis`, `hand_r` — confirmed 2026-07-26 via `get_socket_bone` after creating `RightHandSocket`). **Workaround for affected bones**: drive the real Skeleton Tree UI via `SlateInspectorToolset` instead — right-click the target bone → "Add Socket" → rename via F2 — then verify with `get_socket_bone` (that read-only query tool is reliable; it's specifically scripted socket *creation* that's broken, and only for some bones).
- **`UMGToolSet` exists and can build a Widget Blueprint's Designer-tab hierarchy end-to-end** (`CreateWidgetBlueprint`/`AddWidget`/`GetWidgets`/`GetWidgetDescription`/`GetWidgetTreeDepth`/`CompileWidgetBlueprint`) — not previously documented in this file, confirmed 2026-08-04 via `Docs/Planning/MCPWidgetBuildTest_2026-08-04.md`/`_Report.md`: a 14-node hierarchy (nested Size Boxes/Overlay/Image/Text Block, per-slot Padding, non-uniform sizing) built via MCP tool calls alone matched a written spec exactly, independently confirmed via 3 separate read-back methods (per-node `get_properties`, `GetWidgetDescription`'s full tree dump, and a Designer-tab screenshot via `EditorAppToolset.OpenEditorForAsset` + `CaptureEditorImage`). Two gotchas from that test: (1) unlike a WBP created by hand in-editor, `CreateWidgetBlueprint` starts with a genuinely **empty** tree (`widgetCount: 0`, no default root Canvas Panel) — add one explicitly before attaching anything. (2) `ObjectTools.set_properties`' `values` argument is a JSON **string**, not a JSON object — passing a real object gets a schema-echo error. **Not yet tested**: adding an *instance of an already-built `WBP_ZS_*`* as a child (every real B1 widget nests these — `WBP_ZS_ItemSlot` inside `WBP_ZS_CompartmentPanel`, etc.) and setting a custom C++ class's own `EditAnywhere` properties (`Gear Slot`, `Mount Index`, ...) via this path — confirm both before trusting `UMGToolSet` for a real, `BindWidget`-dependent B1 widget unsupervised.
- **A `UserWidget` whose root is a `CanvasPanel` (the default root for every new WBP) reports `(0,0)` desired size — and renders at 0×0 wherever it's embedded with `bAutoSize:true` — unless at least one of that root panel's direct children has `bAutoSize:true` on its own `CanvasPanelSlot`.** `SConstraintCanvas::ComputeDesiredSize()` (the Slate widget behind `UCanvasPanel`) only measures children flagged `bAutoSize:true`; a `bAutoSize:false` child is assumed to live inside an already-sized canvas and doesn't contribute to the canvas's own reported size, even though its explicit `Offsets` rectangle still positions/sizes it correctly *within* that canvas. Confirmed 2026-08-09 as the real root cause behind 5 Loadout-tab Blueprints (`WBP_ZS_PistolMount`/`MeleeMountSlot`/`EquipmentSlot`/`SecondaryHandSlot`/`EquipSlot`) rendering as present-in-tree-but-invisible: each had a single root-`CanvasPanel`→`SizeBox` child with `bAutoSize:false` (ground-truthed via `ObjectTools.get_properties`, not just `GetWidgetDescription`'s diff-style dump, which only prints non-default properties and can mislead by omission). The one working sibling class (`WBP_ZS_WeaponMountSlot`) had `bAutoSize:true` there and was the tell. Fix is one `set_properties` call per Blueprint (`{"bAutoSize": true}` on the root panel's slot) — check this first on any future `WBP_ZS_*` that "is in the hierarchy, not Collapsed, but doesn't draw."
- **`EditorAppToolset` has real `StartPIE`/`StopPIE`/`IsPIERunning` tools, and property/transform/component queries (`ActorTools`/`ObjectTools`/`SceneTools.find_actors`) against the live `UEDPIE_0_...`-prefixed PIE actor instances are reliable** — confirmed 2026-08-11: a `StartPIE` session ran real gameplay (`LogZombieShooter` lines appeared), and reading `AnimClass`/`SkeletalMeshAsset`/transform/etc. off the actual spawned pawn worked correctly. **But `CaptureViewport`/`GetVisibleActors`/`GetCameraTransform` reflect the underlying *editor* world, not the live PIE duplicate**, even with `playMode: PlayMode_InViewPort` — `GetVisibleActors` only ever returned `/Game/.../Lvl_ThirdPerson` paths (never the `UEDPIE_0_` duplicate), and `CaptureViewport` shots aimed exactly at a live pawn's confirmed transform (cross-checked via `get_actor_transform` on the real PIE instance) never showed the pawn from any of 4 angles including straight-down overhead — only editor-only billboards/gizmos (PlayerStart flag, Arrow component) rendered, because those happen to be real editor-world actors sitting at the same coordinates. Net: use these tools freely to inspect live PIE *state*; don't trust them for visual/rendering bugs (T-poses, invisible meshes, material glitches) — that's still dev-hands-only, see [[feedback_pie_testing_is_hands_only]].
- Also note: `CaptureViewport`'s `captureTransform` and `annotations` params are documented as optional but the MCP wrapper actually requires both to be passed explicitly (errors with "needs a default value" otherwise) — pass a full transform and a zeroed-out/disabled `annotations` object (`gridSpacing:0, maxLabelDistance:0, maxLabels:0, classFilter:{refPath:""}`) to get a clean, unannotated shot. Tool call results embedding a base64 image routinely exceed the MCP text-output token limit and get saved to a `tool-results/*.txt` file instead — decode via PowerShell (`ConvertFrom-Json` → `[Convert]::FromBase64String($obj.returnValue.image.data)` for `CaptureViewport`, note the extra `.image` nesting that `CaptureAssetImage`/`CaptureEditorImage` don't have — `$obj.returnValue.data` for those) → `[IO.File]::WriteAllBytes(...)`, then view with `Read`.
