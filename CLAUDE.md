## Naming (critical)
- `ZS` prefix for all non-zombie classes/assets: `AZSPlayerCharacter`, `AZSGameMode`, `AZSGameState`, `AZSPlayerState`, `AZSPlayerController`, `AZSWeapon`, `UZSHealthComponent`, `UZSWeaponConfig`, `BP_ZS_*`, `DA_ZS_*`, `WBP_ZS_*`.
- "Zombie" reserved only for enemy: `AZombieCharacter`, `AZombieAIController`, `BP_Zombie_*`. Never mix — player must never be confused with enemy.
- Input Actions unprefixed (`IA_Fire`); Input Mapping Contexts prefixed (`IMC_ZS_Default`).

- Build (Editor): Rider/VS → `ZombieShooterEditor Win64 Development`, or `Build.bat ZombieShooterEditor Win64 Development -project=...uproject -waitmutex`

## Architecture
- **Framework/**: `AZSGameMode` (server rules), `AZSGameState` (replicated world clock — `TimeOfDayHours`/`DayCount`/utilities-shutoff timer — plus sleep/time-skip readiness aggregation across `PlayerArray`, and the finite per-session rarity loot pool used by `Inventory/`), `AZSPlayerState` (health/ammo/kills, unpopulated), `AZSPlayerController` (Enhanced Input via `IMC_ZS_Default`+`IMC_ZS_MouseLook`, wired via `ConstructorHelpers::FObjectFinder`, not BP CDO).
- **Player/**: `AZSPlayerCharacter` — TopDown is the **only** camera now (fixed pitch/yaw; `EZSCameraPerspective`/`ToggleCameraPerspective`/the ThirdPerson path were deleted B0-T3.9, dev-confirmed permanent, no fallback). `Player/ZSCameraDirector` (an `ActorComponent`, not self-ticking — the character's own `Tick()` drives it) owns zoom: a push/pop `EZSCameraContext` stack (`Outdoor`/`Interior`/`Underground`/`Driving`-reserved) for auto-zoom presets, plus a manual-override layer (`ApplyManualZoom`) that fully disengages auto-zoom until a context change moves away from wherever the override started. `Framework/ZSElevationSubsystem` (a `UWorldSubsystem`) answers "what Z-plane is this actor on" for `GetCursorGroundLocation`'s ground-plane projection — B0 ships a single-floor stub, B4 swaps the body for real multi-level. Hybrid cursor facing (`UpdateCursorFacing`) overrides actor rotation toward the mouse cursor's ground-plane projection, gated to aiming/attacking/interacting only. Move/look/jump/crouch/sprint/aim/fire/reload/melee are all server-RPC+OnRep replicated. Weapon equip is config-driven through a fixed 9-slot `HotbarSlots` array (`CurrentWeapon` **is** the active slot — deliberately not renamed to avoid a Blueprint-reference-corruption risk, see the Live Coding lesson below); `SelectHotbarSlot` (not `CycleHotbar` — removed B0-T3.4, OQ-B0-01: hotbar is 1-9 direct-select only, scroll wheel is camera zoom) routes through `Server_SelectHotbarSlot`, which schedules the actual equip after `EquipTimeSeconds`/`UnequipTimeSeconds`, gated by `bIsBusy`. `IA_Attack` dispatches on `CurrentWeapon->GetConfig()->AttackType` (`EZSAttackType`, `ZSWeaponTypes.h`) — `Ranged` into a spread-cone hitscan/projectile fire (`Server_Fire`, cone via `FMath::VRandCone`, headshot weighting via a `Hit.BoneName` override — B0-T3.5/T3.6), `Melee`/no-weapon into `PerformMeleeSwing` (shared bare-fist/weapon-melee logic, now costs Stamina per swing and excludes downed zombie targets — B0-T10.3/T10.5). `SecondaryHand` (B0-T11): a GUID slot alongside `HotbarSlots`, holding either a one-handed+`bUsableInSecondaryHand` weapon or any `bIsToggleable` item (a flashlight — `FlashlightComponent`, a real `USpotLightComponent`); `IA_SecondaryAction` dispatches, but only the toggleable-item half actually does anything yet — an offhand weapon validates into the slot but doesn't fire (documented gap, needs its own `AZSWeapon` actor/ammo choreography). `Player/Animation/UZSAnimInstanceBase` = native TP AnimBP parent. **Not yet built**: Shove, Mount/Climb (both bundled on the same `Space` input as the T10.6 finisher, genuinely undesigned).
- **Interaction/**: `UZSInteractableComponent` — attach to any actor to make it interactable; `AZSPlayerCharacter::TryInteract`/`Server_Interact` is the server-authoritative entry point, `UpdateNearestInteractable` does a per-tick sphere-overlap scan against `ECC_WorldStatic`/`ECC_WorldDynamic`. No world-prompt widget yet — `OnNearestInteractableChanged` is the C++ hook for one.
- **Survival/**: `UZSNeedsComponent` — replicated Hunger/Thirst/Fatigue/Stamina/Wet/Temperature, rates/curves from `UZSNeedsConfig`. Hunger/Thirst/Fatigue/Temperature decay/tick on `AZSGameState`'s game-hour clock; Stamina is real-time (drains sprinting — scaled by inverse encumbrance, B0-T4.8 — regens idle), gates `StartSprint`. `Wet` (B0-T4.1, debug-only `Server_SetWet` until B4's weather exists) auto-dries after `WetDryOutGameHours` and feeds both `Temperature`'s target (B0-T4.3, four inputs: neutral/wet/indoor/clothing-insulation-sum) and periodic movement noise (`AZSPlayerCharacter::TickWetFootstepNoise`, B0-T4.2 — dry footsteps report nothing). `GetPerformanceMultiplier()` (Hunger/Thirst/Fatigue/Temperature, performance-only, provably never exceeds 1.0) feeds healing rate/aim accuracy/attack recovery; `GetPerceptionMultiplier()` (Fatigue-driven, B0-T4.6) is a separate presentation-only stub for a future vignette/audio pass, never touches gameplay math. Four `GetXSeverityTier()` accessors (Hunger/Thirst/Fatigue/Stamina/Temperature) share one 4-tier scale off `UZSNeedsConfig`. `UZSItemConfig` is the eat/drink/use data contract, consumed via `Server_ConsumeItem`/`Server_UseItem`; also carries `bIsToggleable` (B0-T11, an activatable item like a flashlight) and `InsulationValue` (clothing → Temperature). Sleep/time-skip: `AZSPlayerCharacter::RequestSleep`/`CancelSleepReady` (per-player ready flag) + `AZSGameState::UpdateSleepRequestState` (all-players-ready aggregation + clock advance); `IsSafeToSleep()` is real for the aggro-cooldown half (`Server_NotifyHostileDetection`, called from zombie perception) but the "real shelter" half is still stubbed `true` (B0-T4.10 — no indoor/barricade system exists, B4's job). No moodle UI yet — `OnHungerChanged`/etc. are the hooks.
- **Weapons/**: `AZSWeapon` (replicated config/fire-mode/ammo; root component `BaseWeaponMesh`, a `UStaticMeshComponent` — no skeletal weapon meshes anywhere), `UZSWeaponConfig` (the full per-weapon data contract: Setup meshes (`BaseWeaponMesh`/`TriggerMesh`/`MagazineMesh`/`TP_Mesh`), Attachments (`MuzzleMesh`/`HandguardMesh`/`GripMesh`/`OpticMesh`, each with its own `SocketX` field), fire/melee/durability/knockback tunables, `AttackType`, aim-cone spread + headshot-weighting fields (`HipFireSpreadDegrees`/`AimedSpreadDegrees`/`HipFireHeadshotChance`/`AimedHeadshotChance`, B0-T3.5/T3.6), jamming fields (`bJamImmune`/`BaseJamChance`/`MaxJamChance`/`TP_ClearJam`, B0-T10.1), `MeleeStaminaCost`/`FinisherMontage` (B0-T10.3/T10.6), and `Handedness`/`bUsableInSecondaryHand` (B0-T2.12) for `SecondaryHand` eligibility), `AZSProjectile` (opt-in per-weapon simulated projectile — `ProjectileClass` unset keeps the old instant hitscan path — replicated movement, damage/knockback/headshot-weighting on first blocking hit), `AZSMagazine` (cosmetic prop, also static-mesh-based), notify classes `AN_ZS_UnlockActions`/`ANS_ZS_BlockADS`/`ANS_ZS_LeftHandGrip`. `AZSWeapon::CurrentConditionQuality` (seeded from the carried `FZSItemInstance`, independent of the melee-only durability system) drives the jam-chance roll (`Server_RollForJam`, called from `Server_Fire` before ammo is consumed) and its own `bIsJammed`/`OnJamStateChanged`; cleared via `Server_ClearJam` (the "Rack Firearm" action).
- **Combat/**: `UZSHealthComponent` — replicated `CurrentHealth` + 4 `FZSBodyZoneWound` (Head/Torso/Arms/Legs), each with a wound type (Scratch/Laceration/Fracture/Bite), bleed/dirty/splinted/amputated flags, a critical-head-bleed flag (`bCriticalBleed`, B0-T5.3, rare roll on a fresh Head bleed, steep override rate until bandaged), multi-day fracture recovery (`FractureRecoveryProgressGameHours` vs. `UZSHealthConfig::FractureRecoveryDurationGameHours`/`SplintedFractureRecoveryDurationGameHours`, B0-T5.4), and a **second, distinct** wound-infection state (`EZSWoundInfectionState`, B0-T6.1 — ordinary dirty-wound infection, escalates past `WoundInfectionOnsetGameHours` if untreated, cured instantly by disinfect/clean-bandage, worsens bleed/slows fracture recovery, never touches `CurrentHealth`) kept separate from bite infection (`EZSInfectionStage`) below. All damage flows through `AZSPlayerCharacter::TakeDamage` (zone inferred from hit bone name — headshot weighting can override this to Head, see Weapons/ above — wound type from the damage type class via `ZSDamageTypes.h`'s marker classes) into `Server_ApplyDamage` — nothing else mutates health directly, per the replication convention below. Bite wounds roll a hidden infection chance; `EZSInfectionStage` progresses on `AZSGameState`'s game-hour clock over a per-infection randomized 2-4 in-game-day total (`Min`/`MaxBiteInfectionDurationGameHours`, B0-T6.4), delayable per-treatment via `Server_DelayInfection`/`UZSItemConfig::MedicalIncubationDelayGameHours` (B0-T6.5) — **plainly, legibly shown in a future UI**, not deliberately ambiguous (B0-T6.3 reversed the original premise). `Server_AmputateZone` clears an active bite infection at the cost of a permanent zone penalty (any zone, solo-capable, no tool-item gate); now a real timed/`bIsBusy`-gated action (B0-T7.1) that ends in `AZSPlayerCharacter::EnterBlackout` — an incapacitated-but-still-damageable state (movement/attack/loadout-switch disabled, not death), auto-recovering after `BlackoutDurationSeconds` (with a solo-only world-clock jump, `BlackoutTimeSkipGameHours`) or endable early by a teammate interacting with the new `ReviveInteractable` (B0-T7.2-T7.4). Arm amputation blocks equipping a `TwoHanded` weapon (B0-T7.5). `GetMobilityMultiplier()`/`GetAttackSpeedMultiplier()`/`GetReloadSpeedMultiplier()` feed move speed and fire-rate timing. Death → `HandleDeath` → `Server_HandleDeathLootAndZombie` (drops every carried instance at the death location via `UZSInventoryComponent::Server_DropAllItems`, then spawns `AZSPlayerCharacter::DeathZombieClass` there — B0-T9.1/T9.2, unset class = content gap) → delayed `Destroy()` + `RestartPlayer` respawn (always the same persistent world, solo included, B0-T9.4). Treatment (`Server_ApplyBandage`/`Server_Disinfect`/`Server_Splint`) and item consumption both route through `Server_UseItem`, dispatching on `UZSItemConfig::EZSItemUseType`.
- **Zombies/**: `AZombieCharacter` — deliberately does not reuse `UZSHealthComponent` (that machinery is player-specific); just a flat replicated `CurrentHealth` seeded from `UZSZombieConfig::MaxHealth`, same `TakeDamage`-only-entry-point rule. A landed hit whose knockback strength meets `AZSPlayerCharacter::DownedKnockbackThreshold` (checked centrally in `ApplyHitKnockback`, so hitscan/projectile/weapon-melee/bare-fist all trigger it identically) enters a temporary **downed state** (`bIsDowned`, `Server_EnterDownedState`/`Server_ExitDownedState`, B0-T10.4) — auto-recovers after `UZSZombieConfig::DownedRecoverySeconds` unless finished first via the player's Space finisher (`AZSPlayerCharacter::Server_PerformFinisher`, B0-T10.6, branches bare-handed-stomp vs. equipped-weapon-downward-strike); a standing melee swing (`PerformMeleeSwing`) unconditionally excludes downed targets (B0-T10.5). `AZombieAIController` wires `AIPerception` (sight+hearing, radii from `UZSZombieConfig` at `OnPossess`) and runs `BT_Zombie`/`BB_Zombie` (`/Game/ZS/Enemy/AI/`) — `HandleTargetPerceptionUpdated` writes Blackboard keys, calls `SetChasing`, and notifies the sensed player's aggro-cooldown (`Server_NotifyHostileDetection`, feeds `IsSafeToSleep()`). `SetDowned` (called from the downed-state transitions above) sets the new `bIsDowned` Blackboard key and, until `BT_Zombie`'s graph is actually wired to branch on it (content gap, no editor/MCP access when this was built), pauses/resumes the whole tree directly via `BrainComponent` as a functional stand-in. `Zombies/AI/` holds all 6 BT task nodes as native C++ (`BTTask_MeleeAttack`/`StartInvestigationTimer`/`StartIdleDwell`/`Wander`/`GetInvestigationPoint`/`ClearLastKnownLocation`, sharing key names via `ZSZombieBlackboardKeys.h`) — no content-Blueprint BT task wrappers. Verified working in PIE (wander/investigate/chase). `UZSZombieConfig` covers speed/health/senses/damage/mesh/anim-class/BT/`DownedRecoverySeconds` per zombie type — a second type is a new config instance, never a C++ branch, per the multi-config rule below. `UZSNoiseSystem::ReportNoise` (wraps `UAISense_Hearing::ReportNoiseEvent`) is wired into weapon fire (`FireNoiseRadius`), sprint start, and periodic wet-footstep movement noise (`AZSPlayerCharacter::TickWetFootstepNoise`). `ZS.SpawnZombies <n>` (host-only console command, `AZSGameMode::StressTestZombieClass`) spawns a scattered batch for profiling (B0-T12.1) — works in any level; the dedicated `Lvl_ZS_StressTest` graybox map itself isn't built (content gap).
- **Inventory/**: `Inventory/ZSItemInstance.h` — `FZSItemInstance` (stable `FGuid InstanceId` + `Config` + `StackCount` + `Location` (`EZSCarryLocation`) + `FZSItemInstanceState` (`CurrentDurability`/`ConditionQuality`, meaningful only when `StackCount == 1`)) is, per B0-T2 Step A (2026-07-26), the one way an item exists anywhere in `Inventory/` — replaces the old bare `Config`+`Count` pairing everywhere except the hotbar/equip slots (see Known gap below). Stackable and per-instance-stateful are mutually exclusive by construction; a merge into an existing stack always discards whichever instance's identity doesn't survive it. `UZSWeaponConfig` now inherits `UZSItemConfig` (B0-T2 Step B) so a carried weapon can exist as a real `FZSItemInstance` at all. `UZSInventoryComponent` — replicated flat `CarrySlots` (`TArray<FZSItemInstance>`) + two equip slots (`EZSEquipSlot::Back`/`Hip`, now `FGuid`s into `CarrySlots`, B0-T2 Step B) granting `CarryCapacityBonus`. `Server_AddItem(Config, Count)` mints fresh instance(s) (new GUID per non-stackable unit); `Server_AddItemInstance(FZSItemInstance)` adds an already-existing instance, preserving its GUID/state if non-stackable or merging its `StackCount` in if not — this is what a dropped weapon's durability survives on re-pickup. `Server_RemoveItem`/`Server_RemoveInstanceById` return the actual instance(s) removed (whole instance if fully consumed, a freshly-GUID'd fragment if only a stack was partially consumed) rather than a bare count, so `Server_DropItem`/`Server_DropAllItems` can hand each one to its own `AZSWorldItemActor`. **Equipping (hotbar and gear slots alike) never physically removes an instance from `CarrySlots`** — a slot just holds a `FGuid` reference into an instance that stays resident there, which is what makes a bag's own contents (`FZSItemInstance::ContainedItems`, `Server_StoreInBag`/`Server_RetrieveFromBag`, B0-T2.9) survive equip/unequip/drop for free, and what `Server_DropAllItems` (B0-T9.1, called on player death) relies on to sweep hotbarred/equipped items too without special-casing them. Loot rolls a `ConditionQuality` (0-1) per instance, banded by rarity tier via `AZSGameState::RollConditionQuality` (B0-T2.10). `GetEncumbranceMultiplier()` folds into move speed alongside `Combat/`'s mobility multiplier — a soft penalty past capacity, not a hard carry block. `AZSWorldItemActor` is a replicated pickup (reuses `Interaction/`'s `UZSInteractableComponent`) holding one `ItemInstance` (`VisibleAnywhere`, code-set only) — `InitializeItem(Config, Count)` mints a fresh instance (the hand-placed/pre-populated-pickup path, e.g. a Blueprint subclass calling it in `BeginPlay`), `InitializeFromInstance(FZSItemInstance)` preserves an existing one (the drop path, called from `Server_DropItem`/`Server_DropAllItems`). `AZSContainerActor` (same interactable reuse) seeds `ContainerSlots` (`TArray<FZSItemInstance>`, `Location = World`) from a `UZSLootTableConfig` at `BeginPlay` and does a "loot all" transfer (`Server_AddItemInstance` per slot) on interact; its `LootTable` field is `EditDefaultsOnly`, so per-archetype containers need a Blueprint subclass (e.g. `BP_ZS_Container_Kitchen`), not a raw placed `AZSContainerActor`. Rare/VeryRare rolls are gated through a finite per-session pool on `AZSGameState`. Reserve ammo is a real, lootable, stackable `UZSItemConfig` too (`UZSWeaponConfig::AmmoItemConfig` names which one a weapon reloads from, B0-T2.11) — no more flat `CurrentReserveAmmo` counter.
- **Replication convention (mandatory)**: `UPROPERTY(ReplicatedUsing=OnRep_X)` + `Server_X()` gated by `HasAuthority()` + `GetLifetimeReplicatedProps()`/`DOREPLIFETIME()` + `OnRep_X()` broadcasts a delegate. Never poll replicated state directly.
- **Multi-config rule**: every weapon or zombie system must generalize to N types via new config data-asset instances, never new C++ branches.
- **Cosmetic attachments must be `NoCollision`**: any mesh rigidly attached to the character (weapon meshes, future held items/clothing) needs collision explicitly disabled. Left at a default blocking profile, it overlaps the owning character's own capsule every tick and `CharacterMovementComponent`'s penetration-resolution logic fights that overlap indefinitely — visible as the character climbing or sliding uncontrollably the instant the mesh attaches. `AZSWeapon::AssignNewStaticMesh` already does this for attachment sub-meshes; anything built directly in a constructor (like `BaseWeaponMesh` itself) needs the same explicit `SetCollisionEnabled(ECollisionEnabled::NoCollision)` call.

## Character Skeleton & Animation
`SKEL_TFA_Mannequin` (Infima's skeleton) is the one shared retarget hub for every humanoid in the project — nothing moves to a different skeleton. Locomotion (idle/walk/run/crouch-walk) comes from **Lyra blend spaces retargeted onto `SKEL_TFA_Mannequin`** (curated into `Content/Animation/ZSAnims/` — Infima's own bundled set has no equivalent directional walk-cycle assets, only static poses), composited via **Layered Blend Per Bone** with Infima's rifle idle/aim poses and montages (fire/reload) for the upper body. A separate raw Lyra/ShooterGame import in `/Game/Animation/` (referencing a never-migrated `SK_Mannequin`) is dead and unused — don't confuse it with the curated `Content/Animation/ZSAnims/` assets.

`ABP_ZS_ThirdPerson`'s AnimGraph: one `BlendListByBool` picks base locomotion (standing vs. crouching) by `bIsCrouched`; a second picks the rifle idle/aim upper-body pose by `bIsAiming`; a `LayeredBoneBlend` layers that pose over locomotion; a third `BlendListByBool` (gated on `UZSAnimInstanceBase::bHasWeaponEquipped`) controls whether the rifle layer applies at all — unarmed shows pure base locomotion with no rifle layer. See the MCP tooling lessons below for the AnimGraph editing workflow and a `BlendListByBool` indexing gotcha.

Scope rule: animation only earns inclusion if readable at gameplay cam distance or gates gameplay timing. Full authorized list + architecture detail: `Docs/GameDevPlan.md` §5.1.

## Conventions
- Epic naming standard (`AMyActor`, `UMyComponent`, `FMyStruct`, `EMyEnum`, `IMyInterface`) + ZS/Zombie rule.
- Booleans: `b` prefix. Pointers: `TObjectPtr<T>` in UPROPERTY, raw `T*` locally.
- `GENERATED_BODY()` on all reflected classes.
- Server mutators prefixed `Server_`. No magic numbers — tunables in `UZSWeaponConfig`/EditAnywhere. Damage only via `TakeDamage()`/`ApplyDamage`. No commented-out code — use branches. Check `Build.cs` before adding heavy modules.
- **Tech split**: C++ = base classes/data contracts/perf-sensitive/shared machinery. Blueprint = gameplay config/tuning. Player/weapon action functions are `BlueprintNativeEvent` so BP children can override without recompiling. AnimGraphs/data assets/BT stay Blueprint.

## Workflow Efficiency (lessons, keep this section short)
- **Don't auto-attempt `Build.bat` while the editor's likely open.** It fails on the Live Coding lock nearly every time (see below) — a wasted round-trip for zero information. State that a rebuild is needed and let the dev trigger it (Rider/Ctrl+Alt+F11), rather than spending a call finding out again.
- **Live Coding (Ctrl+Alt+F11) can silently corrupt Blueprint references to native classes, project-wide, on any patch — broader than just "the class that changed."** Two confirmed incidents, 2026-07-21, same session: (1) after a patch added new `UPROPERTY`s to `AZSPlayerCharacter`, `BP_ZS_PlayerCharacter`'s parent-class link broke (`BlueprintGeneratedClass BP_ZS_PlayerCharacter_C is not a child class of Class ZSPlayerCharacter`), so `AZSGameMode`'s `ConstructorHelpers::FClassFinder` silently fell back to the raw C++ class (wrong pawn, no BP CDO defaults, e.g. no mesh). (2) Separately, three unrelated Blueprints (`BTTask_MeleeAttack`/`StartInvestigationTimer`/`StartIdleDwell`) each had a `Cast To ZombieAIController` node break (`this cast has an invalid target type - was the class deleted without a redirect?`) even though `AZombieAIController`'s header hadn't changed that round at all - the corruption surfaced only once those Blueprints were first *loaded* post-patch (triggered here by an unrelated `unreal-mcp` property read), not at patch time itself. **The real rule: Live Coding reinstances every class in the module on every patch, so any Blueprint anywhere with a cast/reference to a native class in that module is at risk, whether or not that specific class was touched.** No crash, no visible editor error in either case - just silently wrong behavior. Diagnosed both via `EditorToolset.LogsToolset.GetLogEntries`/`BlueprintTools.compile_blueprint`, not guessing. **When a dev reports something that "should just work" behaving wrong after a Live Coding recompile, check the Output Log for `is not a child class of` or `invalid target type` before anything else** (or proactively run `BlueprintTools.compile_blueprint` on any Blueprint about to matter for a test). Reopening/recompiling a broken Blueprint parent-link self-heals; a broken Cast node needs the node itself deleted and recreated (compiling alone doesn't fix it - confirmed via `compile_blueprint` still failing with the stale node in place). Prefer a full editor Compile or `Build.bat` over Ctrl+Alt+F11 whenever practical, and after any Live Coding patch, consider a "Compile All Blueprints" pass (Content Browser bulk action) before trusting PIE results.
- **Check for a running editor with PowerShell's `Get-Process`, not Bash's `tasklist //FI`** — confirmed 2026-07-21 that a `tasklist` image-name filter run through the Bash tool silently matched nothing (wrong quoting through the POSIX-shell layer) while `UnrealEditor.exe` was, in fact, running; `Get-Process | Where-Object ProcessName -match "Unreal|LiveCoding"` caught it correctly. Also: **invoke `Build.bat` via the PowerShell tool, not Bash** — Bash's quoting mangles the batch file's internal `%~dp0`-style calls on this machine (`'C:\Program' is not recognized...`) even when the outer command looks correctly quoted; PowerShell runs it cleanly.
- **`Docs/SessionHandoff.md` is the sole owner of verification status** ("compiled?", "PIE-tested?", "what's next"). `CLAUDE.md`'s Architecture section describes what exists / current-state design — don't restate compile/test status in more than one place, or every status change becomes a multi-file edit.
- **Use targeted reads for large, mostly-static docs** (`GameDevPlan.md`, long class headers) — `Grep` with context or `Read` with offset/limit — instead of reading the whole file when only one section is relevant.
- **Keep TaskCreate/TaskUpdate granularity coarse** — one task per major deliverable/system, not per file. Fine-grained tasks multiply tool-call round-trips without adding real visibility for a solo-dev session.

## MCP / Editor Tooling (lessons, keep this section short)
- `.mcp.json` only proposes the `unreal-mcp` server; actual enablement lives in `.claude/settings.local.json` (gitignored) — won't exist on a new machine until recreated.
- `describe_toolset` on a large toolset (e.g. `BlueprintTools`) can return 70K+ characters — don't call it broadly. Prefer calling a tool blind with a guessed schema first; the error response echoes the exact required schema, which is cheaper than a full describe dump.
- Simulated PIE input (keypresses, viewport clicks) via MCP does **not** reliably reach the pawn — confirmed 2026-07-20 (a simulated `W` never moved `CharMoveComp.Velocity`). Don't spend calls trying to force real gameplay-input verification headlessly; that needs the dev's hands, same as every past multiplayer/input check in this project.
- Poking a replicated/movement-authoritative property directly via `ObjectTools.set_properties` (e.g. `ACharacter::bIsCrouched`) can silently revert next tick if the owning component re-derives it every frame (e.g. from `bWantsToCrouch`) — a "successful" write isn't proof the state actually changed.
- **AnimGraph editing**: `read_graph_dsl`/`write_graph_dsl` return empty for AnimGraph-specific node types (`AnimGraphNode_*`) — use `find_nodes`/`get_node_infos`/`create_node`/`connect_pins` instead, which do support them. Normal EventGraphs (Blueprint logic, not AnimGraphs) work fine with `read_graph_dsl`/`write_graph_dsl`.
- **`FAnimNode_BlendListByBool`'s branch indexing is inverted from the naive bool-to-int mapping**: `bActiveValue == true` selects `BlendPose_0` (index 0), `false` selects `BlendPose_1` (index 1). `create_node`/`connect_pins` don't validate node *semantics*, only pin *connections* — when wiring a new `BlendListByBool`, verify the true/false assignment against a known-working sibling node's wiring, not against intuition.
- **`SkeletalMeshTools.add_socket`'s `bone_name` argument silently fails for at least some bones** (confirmed for a real, non-virtual bone on this project's skeleton — `weapon_r`, verified via the Skeleton Tree UI) — the new socket ends up parented to `root` instead, with only an oblique `SetSocketParent... bone named 'None'` log line as a clue, no thrown error. Works fine for other bones (e.g. `pelvis`, `hand_r` — confirmed 2026-07-26 via `get_socket_bone` after creating `RightHandSocket`). **Workaround for affected bones**: drive the real Skeleton Tree UI via `SlateInspectorToolset` instead — right-click the target bone → "Add Socket" → rename via F2 — then verify with `get_socket_bone` (that read-only query tool is reliable; it's specifically scripted socket *creation* that's broken, and only for some bones).
