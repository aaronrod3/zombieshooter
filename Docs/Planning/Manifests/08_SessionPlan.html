02

Four Session Archetypes

Almost every session is one of these. Naming the type up front — even just to yourself — keeps a session from drifting into a second kind of work mid-stream.

Design & Decision

Resolving an open question, scoping a new system before code exists.

Open
  • Manifest 02 §05 (open questions)
  • The relevant B*.md phase file
  • 90_OpenQuestions.md
Output

A dated decision recorded in the phase file — not code.

Implementation

Building or fixing a specific T-numbered task from a current-tier phase file.

Open
  • Manifest 02 (confirm the tier)
  • Manifest 09 (find the code)
  • Manifest 03 (confirm the status claim)
Output

Compiled, PIE-tested where possible, committed. SessionHandoff.md updated at session end.

Content & Blender

Modeling, texturing, or animation-sourcing work.

Open
  • Manifest 07 (the queue, top to bottom)
  • Manifest 04 (cross-check status)
Output

Assets in the correct folder per Manifest 07 §01, checklist entries flipped from gap to done in Manifest 04.

Review

Verifying an already-built mechanic actually does what was intended.

Open
  • Manifest 09, the relevant section
  • The actual source file it names
Output

Confirmed-correct, or a filed bug — plus a fix to Manifest 09 if the code has drifted from what it says.

04

Starting Any Session

  1. Read Docs/SessionHandoff.md — what was last completed, what's next.
  2. Check Manifest 02 — confirm which tier is active and that nothing there has been superseded.
  3. Name the session's archetype (§02 above) before opening any file.
  4. Post a confirmation summary before doing any work: what this session covers, the exact manifest sections/queue items in play, and any open question from Manifest 02 §05 or the relevant checklist that needs an answer first. Wait for an explicit go-ahead — don't start executing on the assumption silence means yes.
  5. Open only the manifests that archetype needs — don't load all nine into context by default.
  6. Scope one task. Keep phases small and testable; ask before any design-shaping decision rather than guessing (standing project convention).
  7. Commit after each sub-task, not at session end.
  8. At session end: rewrite SessionHandoff.md once — this manifest set doesn't own status, that file still does.
05

Keeping the Set Current

A stale checklist is worse than no checklist. Cheap rule: whoever finishes a task that a manifest tracks flips its status in the same session, not later.

ManifestUpdate trigger
01 LoreOnly on a real story decision — this is meant to be stable
02 Priority TrackA tier completes, or scope inside one changes materially
03 Interactions LedgerAny mechanic moves between Built / Planned / Gap
04 Content ChecklistAny item, skin, animation, audio, or VFX asset lands
05 EnvironmentsThe B2-T2 kit decision lands, or any building/POI gets built
06 Comparable GamesRarely — re-research only if a whole new system category enters scope
07 Blender Bench SheetEvery Blender session — reorder the queue as items land or new gaps surface
09 Code & Mechanic MapAny function/class named in it gets renamed, moved, or reworked
