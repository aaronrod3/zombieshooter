**4 real production-code bugs found and fixed:**
1. **`AZSWeapon::CanReload()` blocked reloading entirely on a freshly-equipped weapon** until it had been fired at least once — `InitializeFromConfig` seeds phantom full ammo (`CurrentMagazineAmmo = MagazineCapacity`) with no real magazine loaded (`CurrentMagazineInstanceId` invalid), and the old fullness check couldn't tell that apart from "a real magazine is already loaded and full." Fixed: the fullness short-circuit now only applies when `CurrentMagazineInstanceId.IsValid()`. This was blocking real gameplay, not just the test.
2. **`UZSHealthComponent::GetWoundDisplayCondition` returned `Fracture` for a Head/Torso zone** even though those zones "feed no gameplay multiplier" per this function's own documented contract — the Fracture check sat ahead of the Arms/Legs zone gate instead of behind it. Fixed: Fracture now shares the same zone gate the generic `Wounded` fallback already used.
3. **`TickFractureRecovery`/`TickWoundInfection` didn't pause on `bIsDead`** (unlike their siblings `TickBleed`/`TickInfection`) — a corpse could keep accumulating fracture-recovery/wound-infection progress during its post-death linger window. Fixed: added the missing guard to both.
4. **Extraction (`Server_RequestExtraction`) never wrote back live weapon durability/ammo or destroyed the equipped `AZSWeapon` actor before banking items to the hub stash** — the exact bug class the death path (`Server_HandleDeathLootAndZombie`) was already fixed for once, just never applied to the newer extraction path. Extracting while holding a weapon would have banked a stale-condition weapon to the stash and leaked the live `AZSWeapon` actor. Fixed by extracting the death path's weapon-teardown sequence into a shared `AZSPlayerCharacter::FlushAndDestroyEquippedWeapons()`, called from both paths now.

**3 "mysterious" long-standing test failures turned out to be test bugs, not production bugs** — all the same root cause: `Inventory->GetCarrySlots().FindByPredicate(...)` calls `FindByPredicate` directly on a temporary `TArray` returned by value, then reads through the resulting dangling pointer (`GetCarrySlots()` documents itself as "returns a copy, not a reference"). Confirmed via an actual runtime log from a past automation run, not just re-reading the code. Fixed at all 10 occurrences across 5 test functions (`ZS.Inventory.EquipHelmetForceUnequipsHead`, `ZS.Inventory.CompartmentCapacityAndStoreRegression`, `ZS.Weapons.MagazineReloadSwapsInstance`, and 2 already-passing tests that had the same latent bug harmlessly) by storing the array in a named local first — the exact pattern this project had already fixed once before (see the dangling-pointer bug noted in an earlier session).

**`ZS.Inventory.BagStoreAndRetrieve`'s "second food found" failure**: `DA_ZS_ItemConfig_CannedFood` is a real stackable content asset, so a second `Server_AddItem(FoodConfig, 1)` correctly merges into the existing instance's `StackCount` rather than minting a second GUID — the test's premise (two adds → two distinct instances) was wrong, not the production code. Fixed by using a fresh non-stackable filler config for that half of the test instead of reusing the real stackable content asset.

**`ZS.Combat.DownedZombieAutoRecovery`/`ZS.Health.AmputationChoreographyAppliesShock` root-caused as a genuine test-harness limitation**, not a logic bug: traced against the actual UE 5.8 engine source and confirmed `UEditorEngine::Tick()` never ticks an `EWorldType::Game` world context outside PIE/Editor, so this suite's bare offline test world's `FTimerManager` never advances no matter how long a latent command waits in real time — the recovery/shock timers were correctly scheduled but could never fire. Fixed both latent commands to manually pump `World->GetTimerManager().Tick()` each poll using real elapsed time since the last poll.

**2 zombie-AI test failures (`ZS.Combat.ZombieBiteZoneWeightedRoll`, `ZS.Combat.ZombieDeathWhileDownedClearsDownedFlag`) could not be reproduced by reading the code — both look already-fixed.** Both bugs' original fixes and their regression tests were added in the same past commits, and the current source matches what the tests expect exactly. Likely explanation: stale tracking in this file rather than a live bug (this project has a documented history of a "successful" Rider build silently not recompiling the DLL). **Needs a fresh full rebuild + test run to confirm — don't keep carrying these as "still failing" without re-verifying against a freshly-timestamped build.**

## B1 progress — 2026-08-09 (continued, inventory equip-slot invisibility root-caused and fixed)

**Root cause found and fixed for the 6 non-rendering Loadout-tab widgets flagged below** — `unreal-mcp` reconnected cleanly this session. All 6 traced to the same mechanical bug in 5 Blueprint assets (`WBP_ZS_PistolMount`, `WBP_ZS_MeleeMountSlot`, `WBP_ZS_EquipmentSlot`, `WBP_ZS_SecondaryHandSlot`, `WBP_ZS_EquipSlot` — the last one is the shared class behind every `VBox_ClothingSlots`/`VBox_GearSlots` child, which is why those two VBoxes read as "missing" too): each one's root `CanvasPanel` has a single child `SizeBox` whose `CanvasPanelSlot.bAutoSize` was `false` (confirmed via `ObjectTools.get_properties` ground-truth reads, not just the diff-style `GetWidgetDescription` dump). A `CanvasPanel`'s own `ComputeDesiredSize()` only measures children with `bAutoSize=true` — a `bAutoSize=false` child is assumed to live inside an already-sized canvas and doesn't contribute to the canvas's reported size. With no auto-size child, each of these 5 root panels reported `(0,0)`, which propagated up as the whole widget's desired size — and since `WBP_ZS_Inventory` embeds all of them with `bAutoSize:true` (sizing to the child's desired size), they rendered at literal 0×0: present in the tree, `Visibility:Visible`, but zero pixels. The one known-working sibling class, `WBP_ZS_WeaponMountSlot` (backs `WeaponMountSlot_Primary`/`Secondary`), was the only one with `bAutoSize:true` set correctly — that's what made it the odd one out and the tell.

**Fix applied**: set `bAutoSize:true` on the root-`CanvasPanel`→`SizeBox` slot in all 5 Blueprints via `ObjectTools.set_properties`. All 5 Blueprints plus `WBP_ZS_Inventory` itself recompiled clean and saved to disk. Verified visually via a Designer-tab editor screenshot (`EditorAppToolset.CaptureEditorImage`) — all 6 widgets now occupy correct, non-zero space in the Blueprint's own preview. **This was a real, separate defect and is legitimately fixed**, but it turned out not to be the whole story (see below).

**Dev retested in a genuinely fresh PIE session — still blank.** Root-caused for real this time by reading the actual C++ (not just the earlier source-audit note, which was too narrow — it checked for self-directed `SetVisibility` calls but missed this): `UZSWeaponMountSlotWidget::RefreshIcon`, `UZSEquipSlotWidget::RefreshIcon`, `UZSEquipmentSlotWidget::RefreshEquipmentIcon`, and `UZSSecondaryHandSlotWidget::RefreshSecondaryHandIcon` all called `Image_Icon->SetVisibility(ESlateVisibility::Collapsed)` whenever the slot was empty — and `Image_Icon` is the *only* visual content in any of these widgets (no background/border). **Dev design intent, given explicitly**: equip/mount slots should *never* collapse — an empty slot is still real, visible UI (a future background-image pass will sit behind the icon; right now the priority is getting the UI structurally correct, not final art). **Real fix applied** (`.cpp`-only, all 4 files, Live Coding-safe — no header/signature changes): replaced the `if (empty) { SetVisibility(Collapsed); return; }` branch in all 4 `Refresh*Icon()` functions with the same always-visible/clear-brush-when-empty pattern already used by `UZSItemSlotWidget`. **Written, not yet compiled** — needs a Live Coding patch (Ctrl+Alt+F11) or full rebuild, then a genuinely fresh PIE retest.

## Known tooling gotchas (worth remembering)

- No PIE-input automation path exists — every manual test in `B0_ChecklistAndDecisions_2026-07-26.md` genuinely needs your hands.

- The automation-test command's `-log=name.log` argument didn't take effect in practice 2026-07-30, but did work correctly 2026-08-01 (two separate runs, both produced the named file) — inconsistent, cause unknown. - A component added to an actor post-spawn via `NewObject`+`RegisterComponent()` does **not** reliably get `BeginPlay()` called in a synthetic (non-PIE) world — needs to be a real constructor subobject instead, or `DispatchBeginPlay()` called explicitly.
- **`UWidget` already declares its own `Slot` property** (`TObjectPtr<UPanelSlot> Slot` — the panel slot a widget occupies in its parent). Naming anything `Slot` in a `UWidget`-derived class collides with it — as a `UPROPERTY` it's a hard UHT error ("shadowing is not allowed"); as a plain local variable inside a member function it's MSVC's C4458 ("declaration hides class member"), which this project's build treats as an error too, not just a warning. Confirmed both flavors 2026-08-02 building the B1 widget classes. Avoid `Slot` as an identifier anywhere in `UI/` — use `GearSlot`, `ItemSlotWidget`, etc. instead.
