Building an Item, Start to Finish

How ZombieShooter's item system actually works, and the exact steps to turn a mesh into a real, pickup-able, equip-able game item — grounded in the current C++ and Content trees, not a proposal. Includes a fresh read of Content/ZS/Items/Food/: 14 meshes are already staged there with no item behind them yet, and one — canned beans — already has a baked icon (T_CanofBeans). §12 maps all of it to what to build next.

01 · Guide

Quick Start — Add a New Item

The full path from nothing to a lootable, equippable item. Each step links to the reference section with the actual detail.

  1. Pick something already staged, when you can. §12 lists 14 meshes sitting in Content/ZS/Items/Food/ with no item config behind them yet — starting there skips sourcing a new mesh entirely.
  2. Pick the archetype (§11) and confirm which fields it needs beyond the base 6 (§02).
  3. Create the data asset — DA_ZS_ItemConfig_<Name> or DA_ZS_WeaponConfig_<Name> — in the right folder per §10's real convention (e.g. Items/Food/<Category>/, Weapons/<Category>/).
  4. Fill the base 6 fields (DisplayName, WorldMesh, Weight, Rarity, ItemSize) plus whatever the archetype needs — see §11's table.
  5. Generate the icon with BP_IconGenerator (§09) — bake to Content/ZS/Items/Textures/T_<Name>, assign to Icon.
  6. Assign WorldMesh (already sitting in the item's folder if it came from §12), and WornMesh if the item is equippable clothing/gear.
  7. Set ItemSize per the hierarchical compartment rule (§04) and Rarity.
  8. If lootable, add a weighted entry to a UZSLootTableConfig (§08) — e.g. DA_ZS_LootTableConfig_Basic.
  9. Wire up a pickup for testing — extend BP_ZS_WorldItem_Test, or drop the new config into BP_ZS_Container_Test's loot table.
  10. PIE test the whole loop: pick up → icon/stack render correctly in the inventory grid → move between compartments (non-weapon items) → equip (if applicable).
02 · How It Works

Base Classes

Every item and weapon in the game is one instance of one of two UPrimaryDataAsset classes. There is no per-item C++ — a new item is always a new data asset instance, never a new branch (the project's multi-config rule). UZSWeaponConfig inherits UZSItemConfig, so a carried weapon is a real, first-class FZSItemInstance too — it can sit in a carry slot, get looted, and be dropped exactly like a can of food.

class UZSItemConfig : public UPrimaryDataAsset
Source/ZombieShooter/Survival/ZSItemConfig.h

The base data contract every item — consumable, medical, ammo, bag, clothing, tool, or weapon — is authored from. AZSPlayerCharacter::Server_UseItem is the single dispatch point: it reads ItemUseType and routes to the right component, so neither the needs system nor the health system knows about item content directly.

Invariant: stackable and per-instance-stateful are mutually exclusive by construction. MaxStackSize > 1 means InstanceState is never read — a stack of 12 canned foods has no individual durability, a stack of 1 weapon does. This matters for the Food items in §12: give every consumable a real MaxStackSize (canned goods stack, a weapon or bag never does).

Inventory & Equip Architecture

UZSInventoryComponent (Source/ZombieShooter/Inventory/ZSInventoryComponent.h) owns everything above at runtime: a flat CarrySlots list, the 12-entry EquippedSlots array, and 4 weapon-mount slots. Equipping never physically removes an instance from CarrySlots — a slot just holds a GUID reference, which is what lets a bag's own contents survive equip/unequip/drop for free.

Mount slotGateKey
MountedLongGuns[2]Handedness == TwoHanded (a two-handed melee weapon mounts here too — "long gun" is a naming holdover)1 / 2
MountedSidearmOneHanded + AttackType == Ranged3
MountedMeleeOneHanded + AttackType == Melee — exact converse of Sidearm's gate4
EquipmentSlotInstanceIdAny carried UZSWeaponConfig, no gateG
A weapon becomes key-selectable purely by being mounted — there's no separate "assign to slot" step. SelectHotbarSlot / Server_SelectHotbarSlot resolve a 0-based weapon-key index live from whichever mount it maps to, then schedule the actual equip after EquipTimeSeconds. None of this applies to Food/consumables — they never occupy a mount, only a carry slot or compartment.

09 · How It Works

Icon Pipeline

Content/ZS/Items/IconCreator/ holds a working icon-capture rig — not a proposal anymore, it produced the project's first real baked icon (T_CanofBeans). This is the tool every future item's Icon field gets filled from.

AssetRole
BP_IconGeneratorThe capture rig actor — a Scene Capture 2D framing a target mesh and rendering it to a texture. Location: Content/ZS/Items/IconCreator/.
RT_IconThe shared Render Target 2D the rig captures into.
M_IconMaterial reading RT_Icon — most likely used to preview the live capture before baking.
What's confirmed vs. inferred. These three assets and their location are real — confirmed from the Content tree. Their exact exposed variables and click-path aren't readable from the binary .uasset files, so the workflow below is the standard Scene-Capture-to-icon technique this rig almost certainly implements, cross-checked against its one confirmed output. Open BP_IconGenerator in-editor the next time you use it and confirm the exact steps — then this note can be replaced with the real click-path.

Observed output convention (real, from T_CanofBeans)

  • Baked textures land in Content/ZS/Items/Textures/, alongside IconCreator/, not inside it.
  • Named T_<ItemName> — no Icon_ infix. This is the naming actually in use; follow it for the next one.

Workflow

  1. Place or find BP_IconGenerator in a scratch/void area of a level (so nothing else bleeds into frame).
  2. Set its target mesh to the new item's WorldMesh.
  3. Frame and light the capture, then trigger the capture into RT_Icon.
  4. Right-click RT_Icon → Create Static Texture, saving into Content/ZS/Items/Textures/ as T_<ItemName>.
  5. Assign the resulting texture to the item's Icon field.

Key settings, at a glance

SettingValueWhy
Projection TypeOrthographicNo perspective distortion on the icon.
Render Target formatRTF_RGBA8Needs an alpha channel to key out the background.
Post Process alpha supportEnabledProject Settings → Rendering — required for a transparent capture to actually carry alpha through.
Capture scopeShow Only ListOnly the target mesh renders — nothing else in the level.

Rules to follow, read off the tree above

  • Data assets stay flat directly in their category folder (Items/, or Weapons/<Category>/) — DA_ZS_ItemConfig_<Name> / DA_ZS_WeaponConfig_<Name>.
  • Source meshes for a content family get their own subfolder tree under Items/<Family>/<Subcategory>/ — Items/Food/ mirrors the source pack's own categorization (Water/Canned/Meat), not an invented scheme.
  • A single-mesh item sits flat in its subcategory folder — only give it a dedicated nested folder if it's a genuinely multi-part/modular mesh (like the source pack's burger/pizza sets). Canned/Beans/ and Canned/CatFood/ currently break this pattern for a single mesh each — worth flattening to match Canned/SM_Canned_Meat.uasset's sibling pattern before Food scales further.
  • Weapon category folders are named after the weapon class, not the specific gun — Rifle/, not AssaultRifle/ — leaving room for a second rifle later with no rename.
  • Generated tooling lives in its own folder (Items/IconCreator/); baked output lives separately (Items/Textures/), never mixed with the source meshes or the tooling that made it.

Two design calls this list surfaces, not code tasks.

1. Raw/Cooked/Rotten has no supporting mechanic in code today. FZSItemInstance has no timestamp or state-transition field — nothing ages a Raw fillet into Rotten, and nothing currently exists to "cook" one item into another. The 3 meshes per meat almost certainly imply 3 separate, statically-authored item configs (a cooking station or campfire interaction consuming Raw and granting Cooked would be new C++, not content) — worth confirming that's the intended scope before authoring all 9 meat variants as if a live transition exists.

2. DA_ZS_ItemConfig_CannedFood (the existing generic placeholder) overlaps with the 5 new specific canned-good meshes. Worth deciding whether it's retired once CannedBeans/CannedMeat/CannedPeaches/Tuna/CannedCatFood exist as their own items, or kept as a catch-all fallback.

14 · Watch For

Known Issues

Doesn't block reading this guide — these affect trusting specific behavior in PIE, or authoring against a field that isn't what it looks like.

verify

Inventory/equip/loadout rework's compile status isn't confirmed as of this guide's last scan — build and PIE-test before relying on exact runtime behavior in §07.

content

DA_Bag's EquipSlot needs a manual in-editor check. Two past enum renames (Hip→Duffle, Back→Backpack) risk it silently resolving to None on load.

review

DA_ZS_ItemConfig_PistolPickup's status is unclear — may be a stale test asset superseded by DA_ZS_WeaponConfig_Pistol. Needs a dev call before it's treated as real content.

naming

DA_Bag / BP_ZS_Bag / BP_Ammo don't fully match the DA_ZS_ItemConfig_<Name> convention (DA_Bag omits the "ItemConfig_" segment) — worth a rename pass once new content stabilizes the pattern.

content

No weapon has a confirmed AmmoItemConfig assignment — can't verify from binary; check in-editor now that all 4 ammo types exist.

content

DA_ZS_WeaponConfig_Pistol still inherits the rifle's aim-cone defaults (5°/1°) instead of its own intended numbers (8°/2°).

content

11 worn-mesh sockets don't exist on the skeleton yet (SocketHead/Eyes/Mask/Chest/Pelvis/Feet/Waist/Back) — relevant the moment any Food-adjacent clothing/gear item authors a WornMesh.

unknown

Loot table cross-references can't be verified from the binary asset — confirm which items DA_ZS_LootTableConfig_Basic actually rolls in-editor before assuming a new Food item is reachable in play just because it has an entry.
