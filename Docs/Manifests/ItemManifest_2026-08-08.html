01 · Data Model

Base Classes

Every item and weapon in the game is one instance of one of two UPrimaryDataAsset classes. There is no per-item C++ — a new item is always a new data asset instance, never a new branch (the project's multi-config rule). UZSWeaponConfig inherits UZSItemConfig, so a carried weapon is a real, first-class FZSItemInstance too — it can sit in a carry slot, get looted, and be dropped exactly like a can of food.

class UZSItemConfig : public UPrimaryDataAsset
Source/ZombieShooter/Survival/ZSItemConfig.h

The base data contract every item — consumable, medical, ammo, bag, clothing, tool, or weapon — is authored from. AZSPlayerCharacter::Server_UseItem is the single dispatch point: it reads ItemUseType and routes to the right component, so neither the needs system nor the health system knows about item content directly.

Invariant: stackable and per-instance-stateful are mutually exclusive by construction. MaxStackSize > 1 means InstanceState is never read — a stack of 12 canned foods has no individual durability, a stack of 1 weapon does. Merging two instances into one stack discards whichever instance's identity doesn't survive.

Pickup & Container Actors

Two replicated actor classes present an FZSItemInstance physically in the world. Both reuse P1's UZSInteractableComponent rather than a bespoke interaction path.

class AZSWorldItemActor : public AActor
Source/ZombieShooter/Inventory/ZSWorldItemActor.h / .cpp

A single dropped or hand-placed pickup, holding exactly one ItemInstance. Never moves once spawned (no physics-drop-and-settle in v1).

MemberPurpose

InteractableComponentVerb text is generated live: "Pick up <DisplayName> x<Count>".

HandleInteracted2026-08-06: rejects the pickup and leaves the actor alive if Server_AddItemInstance fails (Pockets full) — no longer destroys on a failed add.
class AZSContainerActor : public AActor
Source/ZombieShooter/Inventory/ZSContainerActor.h / .cpp

A lootable container (cabinet, crate...). Seeds ContainerSlots from a UZSLootTableConfig at BeginPlay (server-only). Since 2026-08-05, interacting opens the real WBP_ZS_ContainerLoot screen rather than auto-looting everything.

MemberPurpose
LootTableEditDefaultsOnly — per-archetype containers need a Blueprint subclass (e.g. BP_ZS_Container_Kitchen), not a raw placed actor.

The Weapon Actor

A carried UZSWeaponConfig instance only ever spawns a runtime actor when it's actively equipped — a merely mounted weapon is just a GUID reference, no actor exists for it.

class AZSWeapon : public AActor
Source/ZombieShooter/Weapons/ZSWeapon.h / .cpp

The live, replicated instance of an equipped weapon — assembled entirely from its UZSWeaponConfig at InitializeFromConfig. Root component is a static BaseWeaponMesh, no skeletal weapon mesh anywhere.

06 · Systems

Inventory & Equip Architecture

UZSInventoryComponent (Source/ZombieShooter/Inventory/ZSInventoryComponent.h) owns everything above at runtime: a flat CarrySlots list, the 12-entry EquippedSlots array, and 4 weapon-mount slots. Equipping never physically removes an instance from CarrySlots — a slot just holds a GUID reference, which is what lets a bag's own contents survive equip/unequip/drop for free.

Mount slotGateKey
MountedLongGuns[2]Handedness == TwoHanded (a two-handed melee weapon mounts here too — "long gun" is a naming holdover)1 / 2
MountedSidearmOneHanded + AttackType == Ranged3
MountedMeleeOneHanded + AttackType == Melee — exact converse of Sidearm's gate4
EquipmentSlotInstanceIdAny carried UZSWeaponConfig, no gateG
A weapon becomes key-selectable purely by being mounted — there's no separate "assign to slot" step. SelectHotbarSlot / Server_SelectHotbarSlot resolve a 0-based weapon-key index live from whichever mount it maps to, then schedule the actual equip after EquipTimeSeconds.

13 · Authoring

Icon Pipeline — Scene Capture → Static Texture

A candidate answer to the §11 gap ("no icon has ever been imported, no pipeline exists") — Scene Capture 2D rendering a mesh into a Render Target, then baked to a real UTexture2D and assigned to UZSItemConfig::Icon. This is UE5's one standard, well-documented approach to the problem, not one option among several.

How this was compiled — read before treating it as verified. The chapter breakdown below was pulled directly from the source video's own metadata (real, not guessed). A full spoken transcript wasn't recoverable — the video has no manual captions, and its auto-generated captions didn't reliably re-sync when scrubbed programmatically. The steps and settings below therefore follow that real chapter structure but are reconstructed from the standard UE5 Scene-Capture-to-icon technique, not quoted from the narration. Sanity-check the exact clicks against the video itself before building against this blind.

Build steps

  1. Set up the capture rig. New Actor Blueprint (e.g. BP_IconCapture), placed in an empty void area so nothing else bleeds into frame. Add a Scene Capture Component 2D. Create a Render Target 2D asset sized to icon resolution (match whatever convention §11's icon-pipeline gap settles on) and assign it to the capture component's Texture Target. Add a Static Mesh Component as a child, exposed as an editable variable, so the same rig captures any item's mesh.
  2. Frame it orthographically. Set Projection Type = Orthographic (kills perspective distortion) and tune Ortho Width to frame the mesh consistently regardless of its actual size.
  3. Isolate and light the subject. Restrict the capture to only the target mesh (Show Only List / Show Only Actors) so the rest of the level never bleeds in. Light the rig with its own fixed light(s), not level lighting, so every icon shades consistently.
  4. Capture and bake to a real texture. Call Capture Scene once, on demand. Right-click the Render Target asset → Create Static Texture to bake the live capture into a real UTexture2D that doesn't need the capture rig at runtime.
  5. Strip the background. Enable alpha (Project Settings → Rendering → Enable Alpha Channel Support in Post Processing; Render Target format RTF_RGBA8) so the capture composites transparent instead of baking in a solid color, then re-bake to static.
  6. Wire it into the item. Assign the resulting texture to UZSItemConfig::Icon — the field every content item currently leaves unset (§08).

Key settings, at a glance

SettingValueWhy
Projection TypeOrthographicNo perspective distortion on the icon.

Post Process alpha supportEnabledProject Settings → Rendering — required for a transparent capture to actually carry alpha through.
